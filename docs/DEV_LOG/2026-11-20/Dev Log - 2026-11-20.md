## Important outcome

Guardian's durable Persona attribution was found not to exist, and the finding is not that a feature is missing. It is that the *vocabulary* of Persona had been describing a capability with no substrate beneath it.

Selection and revision resolution are real and exercised. The `PersonaSelectionSnapshot` is frozen at acceptance, is server-owned, is immutable, and cannot be replaced by an acceptance participant — an unreadable canonical selection blocks acceptance rather than falling through to a default, and a revisionless profile is a valid selection meaning "the default profile" rather than a missing one. The worker resolves against the frozen snapshot and never against the thread's current pointer, which is the mechanism by which an accepted turn survives a later profile switch. All of that is proven by code path and by test.

And then it ends. The frozen value exists only in the queued task payload and in a Redis-stream event. It is never written to a durable per-turn record. The assistant message is created with `atomic_completion_meta`, which carries provider, model, selection source, payload summary, retrieval posture and tool-loop observability — and no profile, revision or subject key. `chat_completion_attempts` has fifteen columns and none of them is persona-related. The only durable pointer is `chat_threads.active_profile_id` / `.active_profile_revision`, and `switch_thread_profile` overwrites it. The report's classification is therefore one word: **Missing**.

The deeper half is that stable-subject resolution has the same shape. `ensure_persona_subject` is implemented conservatively and correctly — ownership derived independently of the caller, fail-closed on a missing account binding, validated binding history, refusal of a retired subject — and it has eleven passing tests and **no runtime caller in this checkout**. `create_persona_profile` writes a profile, a binding and revision 1, and no subject. The only two places in the codebase that construct subject rows are the uncalled service and the account-restore path, which restores subjects an archive already contains. So a profile created through `POST /api/persona-profiles` can never be attributed to in the product, and the Memory Vault's attribution route — implemented, tested, and the only caller of a durable attribution path — requires a pre-existing active subject that the product has no runtime operation to create.

Live state confirms it at every layer. Zero of 152,107 messages carry any persona key. Zero `memory_records`, zero `memory_persona_links`, zero `memory_provenance`. One thread of 7,726 carries an active profile; exactly one `thread.profile.switched` event exists in 2,836 outbox rows. The read path is complete and account-scoped, and there is nothing to read.

The report also draws the line that keeps this from becoming a scare: a Persona Subject and a Persona Profile are **unrelated tables with no foreign key between them**, and `persona_subject_bindings.ref_id` is a plain `varchar` pointing at a profile by application-supplied string only. The subject is bound to the profile *identity*, not to a revision, which is exactly what ADR-084 requires and what makes the design sound. The design is right. The wiring was never done. Eight items are listed as genuinely missing, and the report recommends exactly one follow-up: complete the missing capture/attribution seam.

## Closing thought

Two documents landed in this window that answer the same question in the same way, and I did not expect that.

The question is: what is the difference between a capability that is specified and a capability that exists? The vocabulary around Persona said specified. Eleven passing tests, a schema, an ADR requirement, three live rows, a deliberately conservative service, a thread-level pin with a composite foreign key, a migration whose comment says the right thing about what a pin does and does not claim. Every one of those artifacts is correct about itself. And the answer is that a capability is specified when the *last mile* is wired and the *evidence* says so, and the last mile here was missing, and the evidence — 152,107 messages with nothing in them — said so only once somebody looked.

What I respect is that the look was done against the running database and not against the source tree, and that the two were kept apart the entire way through. A report that had read only the code would have said the capability exists, because the code says it exists. The database says it does not. And where the database said something the checkout could not explain — three subjects with no possible creator — the answer given was *working theory, unproven*, rather than a plausible story.

The OpenAI routing contract on `main` is the mirror image of that, and the two belong in the same day. It is a contract whose most important sentences are refusals: exact identity or nothing, structural group markers or unresolved, display names confer no authority, contradictory evidence produces a warning and not a placement. It is what a system should look like when it is built so that being wrong is loud.

And the two operations receipts that stopped before implementation — one at read-only preflight, one at the identity and migration gates — recorded a census instead of a claim. No capture, no two-copy custody, no replacement database, no transfer, no login continuity proof. The honest part is not that they failed; it is that they refused to describe the absence as a result.

The release gate is `HOLD` and stays `HOLD`. Nothing was deployed, three merged surfaces have no dated evidence, two surfaces are `stale`, two have no receipt, and the prose release truth is behind the tip again for a reason that is structural rather than human.

The cheapest thing on this list is also the most revealing: one runtime operation that creates a stable subject, and one column that records which Persona ran a turn. Everything else about Persona is already correct. That is a good problem to have, and an expensive one to leave.

## Narrative Log

The day's shape, once I look at it from a distance, is a single sentence said twice in two different rooms: *the code says the thing exists, and the database says it does not.*

I want to start at the end, because the end is where the day actually landed. At 15:01 UTC a branch that had nothing to do with Persona committed a 1,061-line document whose whole purpose was to ask a narrow question: when Guardian resolves the effective Persona for a chat turn, does that identity survive into durable conversation and memory provenance? The answer was no — and, this is the part that matters, the answer was no in a way that could only be established by looking, not by reading.

Because the code reads well. `guardian/core/persona_subjects.py` implements `ensure_persona_subject` with a conservative, fail-closed algorithm: derive the source's owning account independently of the caller, fail closed if the profile has no account binding, require the authenticated account to own the source, validate that the binding history is contiguous and half-open, refuse a retired subject, and only then create a subject with a fresh UUID and a matching binding. Eleven tests cover it. ADR-084 requires exactly this shape. The database has the tables, with PostgreSQL enforcing account ownership, the binding-pair foreign key and the lifecycle check. There are three live subject rows bound to real profiles, earliest binding dated 2026-09-16.

And no product code calls it. `create_persona_profile` writes the profile, the `PersonaProfileBinding`, and revision 1 — and no subject. `guardian/routes/persona_profiles.py` exposes the CRUD and contains no subject handling of any kind. The only two places in the entire codebase that construct subject rows are the service nothing calls and the account-restore path, which restores subjects an archive already contains.

That is the shape of the trap: every layer of the system was present except the one that would have made it true. You could read any single artifact — the service, the tests, the ADR, the schema — and conclude the capability existed. You had to hold all of them at once and ask where the edges join.

And then the live readback, which is the part that changed my reading of the whole thing. 152,107 chat messages. Zero with `active_profile_id`. Zero with `active_profile_revision`. Zero with `persona_subject_id`. Zero with any persona-prefixed key in `extra_meta` at all. `chat_completion_attempts` has fifteen columns and none is persona-related. The frozen `PersonaSelectionSnapshot` lives in the queued task payload and in a Redis-stream event, and when the turn completes and the task is gone, so is the selection. What remains is `chat_threads.active_profile_id` / `.active_profile_revision` — a single mutable pointer that `switch_thread_profile` overwrites, and which therefore answers a different question than the one you would ask it. One thread of 7,726 carries it. Exactly one `thread.profile.switched` event exists among 2,836 outbox rows.

So: which Persona was effective for that earlier assistant message? During the turn, yes — the snapshot is authoritative and the worker is bound to it rather than to the thread's live pointer, which is precisely the mechanism that protects an accepted turn from a later profile switch. After the turn, no. After a switch, the pointer yields the *current* Persona, which is not the Persona of any earlier turn. The report's classification is one word: **Missing**.

What I keep coming back to is how it was found. Not by a failing test. Not by an audit. By someone asking a narrow question and then refusing to upgrade any code-path claim into a live claim. The report carries its own evidence vocabulary — `proven-live-runtime`, `proven-test`, `proven-code-path`, `documented-contract`, `working-theory`, `aspirational`, `unknown` — and uses it without embarrassment. The three live persona subjects cannot be attributed to a creator from this checkout: the serving tree's revision `f3a9c7d2b8e1` is not present here, so the creator is *unknown*. The working theory is that the serving tree contains a caller this checkout lacks. It is marked **unproven**, because inspecting the serving container's source was out of scope and an unverified story dressed as a fact would have been worse than an open question.

The report also draws the line that keeps this from becoming a scare, and it is the line I would have underlined: a Persona Subject and a Persona Profile are **unrelated tables with no foreign key between them**, and `persona_subject_bindings.ref_id` is a plain `varchar` pointing at a profile by application-supplied string only. A memory's attribution target is the Subject; a thread's execution configuration is the Profile. The subject is bound to the profile *identity* rather than to a revision, which is exactly what ADR-084 asks for and exactly why the design survives a profile edit. The design is right. The wiring was never done. Eight things are listed as genuinely missing, and the report recommends exactly one follow-up: complete the missing capture/attribution seam.

Then there is the small, ugly, useful detail. Fifty-eight threads in the live database carry a `personaId` key in their config — and every one of them carries it with a JSON `null` value. So the legacy persona layer never activates for a single one of them, and with the legacy `personas` table empty, `resolve_persona` falls through to the system default for all fifty-eight. A channel that looked populated was empty, and it looked populated because the key was there.

Now the other half of the day, which is on `main` and is the mirror image of all of that.

The OpenAI import Project-routing stack merged. Thirty-nine files, a new ownership table, a new migration with immutability triggers and a downgrade that refuses to discard placement state, and — the part that will matter — a placement algorithm whose most important sentences are refusals. An exact source conversation identity is required; fabricated, unresolved-prefixed or inconsistent `id`/`conversation_id` pairs fail closed. A group is only a group when it matches `g-p-<32 hex>` with `gizmo_type = snorlax`. Contradictory evidence stays unresolved with a warning rather than being sent to General. An explicitly ungrouped conversation goes to General by *structural role*, not by name. And a fresh Project is never adopted by its display name, because labels are display hints with no authority.

I appreciate that last rule more than I can easily say. The tempting implementation is to match a Project by its label, because that is what a human would do and it is three lines. The rule as written says: a label is a hint, a label can lie, and if you let a label place someone's imported conversations you have built a mechanism for quietly filing another person's history under a project you made up. So placement is driven by structure — the source's own identity — and the display name is allowed to be wrong.

What I also appreciate is that the import stack was corrected three times inside a single UTC day, and that each correction tightened a refusal rather than adding a capability. Route groups by the *selected* account source rather than by whatever the archive happened to carry. Refuse generated conversation identities for project routing — if the importer synthesized the identity, the identity cannot be used to place the thing. Isolate rejected source identity and media evidence so a rejected record's media cannot contaminate the accepted set. Each of those is a small diff that removes a way for the system to be confidently wrong, and together they are the difference between a feature that works on the happy path and one that works on someone's actual archive.

And then the fixture fix, `d9615ce51`, which included the new source dependency in the thread schema fixtures — because without it, eight unrelated suites would have gone red on a missing column and the red would have been noise dressed up as a defect. That is unglamorous and it is the work that keeps the next person's signal clean.

The rest of the day ran in parallel, and its organizing principle was the same: say what you did not do.

The Scout Android campaign added six visual corrections, and each one carries a receipt that names its own exclusions. The source-selector correction fixed a real defect — a clipped **Anthropic** label at 360 dp whose full text was only reachable by an undiscoverable swipe — and the correction renders a labelled row when four labels fit, reserves 48 dp of touch target per option, and falls back to an outlined dropdown at 200% text. The receipt then discloses that TalkBack, physical hardware and a live Guardian connection are outside the fixture, and it excludes one of its own captures by name because the frame duplicated the one before it. A receipt that discards its own bad frame is worth ten that quietly keeps it.

The two operations receipts stopped. One held at read-only preflight and says final capture, two-copy custody and independent recovery remain unverified. The other stopped at the identity and migration gates and says no replacement database, no transfer and no login continuity proof exists. Those are not failures. They are the two receipts doing the thing the whole day was about: recording a census and declining to describe the absence as a result.

ADR-113's identity work is worth a sentence of its own, because it is the second instance of the same shape. The provisioning paths now bind a canonical principal at account creation, writing the `AuthenticatedPrincipal` with its source, operation UUID, actor class and actor ref — the same shape in both the tester path and the Private Preview path. And then the reset script refuses to proceed unless the migration state and the physical principal schema agree, because the pinned parent revision has exactly four principal columns and cannot represent a binding. That refusal is the whole point. A reset script that can silently drop an identity binding is a worse artifact than one that stops and tells you why. And the day had already found, in a completely different subsystem, that the durable record of an identity was the thing most likely to be quietly missing.

So the through-line is this. Three subsystems, one shape. In Persona, a durable attribution record that the vocabulary described and the code implemented but never wired. In identity, a binding that the reset script had to be taught to refuse to destroy. In the OpenAI import, a placement rule that refuses to act on a name. In all four cases the interesting work was not the positive capability but the **refusal** — the negative space, the thing that says no when the evidence is wrong.

And the most expensive artifact of the day was the schema inventory, 5,958 lines of it, because it is the one that says what is physically there without claiming any of it works. Read-only enforcement was verified positively — a write was submitted and the server refused it, which is a stronger statement than "we set a flag." The database was identified from its own Compose labels rather than from its name. Label-filtered `docker ps` was avoided because it has hung on this host before. No application row contents were read, with the single disclosed exception of the `alembic_version` revision, which is migration bookkeeping and is disclosed rather than quietly used.

What this makes possible next is narrow and specific. Not a release. The gate is `HOLD` and it should be: nothing was deployed, three merged surfaces have no dated evidence, two qualification surfaces are `stale` and two have no receipt at all, and the prose release truth is behind the tip for the third consecutive day for a structural reason rather than a human one.

What is possible next is a project in which two specific facts are no longer assumptions. That a memory can be attributed to a stable Persona subject, because a profile's creation creates the subject and a turn records the subject it ran under. And that a reset, a reimport, or a profile switch cannot quietly rewrite the history of who said what.

That is a small list. It is also the difference between a system that can explain itself and one that can be held to account.
