# Dev Log - 2026-11-14

## Summary

2026-11-14 was the day the largest surface movement in Codexify's history landed on `main`, and the day the release truth was forced to say — in the same document, on the same revision — that none of it is proven. Twenty pull requests merged. Scout, Library, Saved Widgets, the scrolling Feed, the Inspector, the sidebar project switcher, the operator-gated retrieval diagnostics, the admission-throttled Preview login, the setup-only OAuth lane. The frontend reorganized its own navigation, the mobile client learned to survive a dropped connection in the middle of a reply, and the backend learned to tell a Redis blip apart from a Redis failure instead of treating both as "stream over".

Underneath that, a second and quieter movement. Three subsystems that can spend money, produce media, or take custody of an import were built today, and every one of them landed *inactive* — the inference budget ledger is default-off, the media and image adapters are dormant, and the import recovery path is on a branch that never reached `main`. The structural question the day raises is not "did the feature ship." It is whether a repository can hold a large amount of unwired capability without that capability quietly becoming reachable, and whether the code says so plainly enough that nobody is misled about it.

The honest answer on 2026-11-14 is: mostly yes, with one exception worth naming. The exception is an operator API key that was redacted from two historical proof documents, where the redaction itself does not establish that the key was revoked.

### Reply-stream recovery, at both ends of the wire (mainline)

- **The backend stopped confusing a transient Redis error with a dead stream** (`722c400b9`). `guardian/guardian_api.py` now distinguishes Redis authentication and authorization errors — which end the stream — from connection and timeout errors, which retry with backoff, and it tracks `read_failures` explicitly. 51 lines of bounds tests carry it.
- **The client learned to reconnect without losing its place** (`fd99c0fb7`). `ScoutTaskEventStreamService.swift` was restructured around a preserved cursor with retry delays of 1, 2, 4 and 8 seconds, deduplicating on event id and checking `isCurrent` so a superseded request stops rather than fighting the one that replaced it. 142 lines of new `ScoutTaskEventStreamTests` cover it.
- **And the client learned to finish what it already accepted** (`2ebf80b3f`). `ScoutComposerFlow` gained `recoverResponse(...)`, which reconciles a pending accepted task using read-only receipt reads and a backoff of 1, 2, 4, 8 seconds plus 28×10 seconds. The rule that makes this correct: *a completed receipt remains pending until the canonical messages have been read successfully* — a completion signal alone is not a delivered answer. Terminal HTTP statuses (400, 401, 403, 404, 422) stop immediately rather than burning the whole retry budget.

### A client that mistook its own guard for a dead backend (mainline)

- **The outage fuse was telling the truth about the wrong thing** (`ccf71d41f`, merged as `#1084`). `frontend/src/lib/api.ts` had been classifying `ERR_BACKEND_OUTAGE_FUSE`, `ERR_CLIENT_RATE_GUARD` and `ERR_CANCELED` as *backend runtime unavailable* — meaning the client's own protective guards and its own cancellations were being reported as the backend having died. Separately, the exemption that lets health and catalog probes through the fuse was regex-based and did not survive URL resolution against the runtime API base, so a genuinely recovered backend could still have its canonical probe blocked. Both are fixed: the three error codes are excluded from the unavailable classification, the exemption is now `isCanonicalBackendProbe(url)`, which resolves each probe against `getRuntimeConfigSync().apiBaseUrl` and compares both origin and path, and a successful preflight now calls `clearBackendOutage()`. 122 lines of tests in `frontend/src/test/api.preflight.test.ts` hold it.

## Important outcome

The structural shift on 2026-11-14 is that **"merged" and "activated" became two different, separately visible states — and the code says so, in the code.** Every new capability that could spend money, emit media, or take custody arrived carrying an explicit marker: *default-off*, *dormant*, *quarantined*, *internal_only*, *inactive*. The budget ledger has a flag. The media adapters are dormant by construction. The Preview OAuth router admits only under an explicit exposure mode with an explicit feature flag on top of it. The retrieval diagnostic answers `404` at the browser-facing origin even though the backend route still exists for operators. This is a repository learning to hold a great deal of unwired capability without that capability quietly becoming reachable — and it is a materially different posture from the one where "on `main`" implicitly meant "on".

The second half of the shift is what the day refused to do. Twenty pull requests landed, the frontend and the mobile client both reorganized substantially, and **not one dated runtime proof artifact was added to `main`**. Every proof document written on 2026-11-14 — the import receiving-resume proof, the inference budget foundation proof — lives on a feature branch. The release-truth document at the tip says the same thing in its own words: the largest surface movement in the window has no evidence, and its posture is code and unit test only. The release gate remains `HOLD`; both `PASS` qualification surfaces are `stale`; both `HOLD` surfaces have no receipt at all. Nothing moved.

What this makes possible is that the next person can tell, without reading a single diff, which parts of this system are real today and which are prepared. That is worth more than it sounds. The failure mode of a codebase like this is not that features are missing — it is that a merged branch gets read as a live capability, an inactive ledger gets read as a spending control, and a setup-only lane gets read as an enabled one. On 2026-11-14 the markers were mostly right. The exception is named in the Notes below, and it is worth not letting it get lost in the volume.
