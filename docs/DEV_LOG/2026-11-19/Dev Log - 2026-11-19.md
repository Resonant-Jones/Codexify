- **The catalog is data, not duplicated code.** Eighteen identities — `image`, `sunburst`, `flare`, `thread`, `doc`, `project`, `workspace`, `profile`, `flow`, `secure`, `connect`, `obsidian`, `codex_entry`, `help`, plus the five composer controls `provider`, `model`, `mode`, `retrieval` and the dual-mode `project`. Each record carries aliases, keywords, scaffold text, interaction modes, declarative effects, availability and a bounded availability reason.
- **Two routes, on the existing router, with the existing dependencies.** `GET /api/chat/slash-commands/manifest` returns the full collection in ascending canonical-token order; `GET /api/chat/slash-commands/search?q=&limit=` returns a ranked subset in the same envelope. Both are mounted on the chat router and inherit its account-session and request-scope dependencies. Successful responses send `Cache-Control: private, no-store`. The routes are omitted from OpenAPI because the internal Command Bus builds its raw manifest from OpenAPI operations.
- **Identity resolution is strict and the failures are named.** Canonical tokens are reserved before aliases are indexed; duplicate IDs, duplicate normalized canonical tokens and alias collisions fail catalog validation; an alias that shadows a canonical token must be removed; ambiguous aliases must be resolved before publication. `/project` is a single record with both modes and `/repo` resolves to it, while `/workspace` stays reserved for its own canonical identity — the backend no longer lists `workspace` as a project alias, and legacy `commandId: "project"` submissions are still accepted on the same terms.
- **Search is bounded and specified.** `q` up to 128 characters; limit 1–25, default 10, out-of-range returns HTTP 422. Ranking is canonical-token prefixes, then alias prefixes, then keyword exact or prefix matches, each group in ascending canonical order, each command appearing only at its best rank.
- **`manifestRevision` makes staleness detectable.** It is a SHA-256 over compact canonical JSON containing the schema version and the ordered commands with sorted keys. It changes with published metadata and is independent of request time, account and search parameters, so a client can invalidate derived lists without re-deriving anything.
- **Availability starts at `unknown`, on purpose.** The catalog read does not evaluate account, thread, turn or client context, so it cannot honestly claim eligibility. Version 1 emits `unknown` for every record with reason `eligibility_not_evaluated`. The contract is explicit that an Obsidian listing establishes no connector configuration, and that query parameters and caller-provided identity hints confer none.
- **The refresh contract is written down.** Fetch after authentication, after reconnecting to Guardian, and after any endpoint or account change. Keep the in-memory snapshot scoped to endpoint and account. Discard the previous snapshot immediately on an endpoint or account change, and discard late responses for a superseded context. A stale snapshot is not evidence of current eligibility.
- **The frontend genuinely stopped duplicating it.** The client contract file shrank by roughly a third and the new hook owns the fetch, the scope invalidation and the revision comparison.

## Important outcome

The day's structural shift is that **a client can no longer be the authority on what the system can do.** Before this change, the slash-command catalog existed in two places — a server-side set of chat intent IDs used for request validation, and a client-side catalog used to render previews and scaffolds. The two were reconciled by hand and could drift. Now there is one registry, on the server, with a versioned read model and a content hash a client can compare, and the contract explicitly denies that reading the catalog tells you anything about whether a given account may act. The third change then tested that new boundary against the most dangerous surface in the product: image generation spends money and reaches an external provider. It did not weaken the boundary to make the feature work. It made the feature require a fresh, successfully loaded, explicitly permitted catalog entry, and it made ordinary English unable to reach the adapter by accident.

The second structural shift is the discipline in the audit. `ddc8ace43` did not ask whether the Android Guardian workspace "looks like" the iOS screens. It asked whether every source-backed relationship in the frozen design language holds in the Compose implementation, and it produced 57 numbered findings with expected rule, observed implementation, measured difference, category, severity, confidence and evidence posture for each. Twenty-one capture files were hashed and then looked at; twelve were excluded by name with a stated reason, and only nine are cited. The APK was identified by hash against the recorded baseline, with the reason a rebuild differs stated rather than papered over. The verdict is deliberately not "parity": it is a list of 46 unmet relationships, a set of three accepted platform variations, two decisions reserved for the operator, and one first slice chosen because a control is currently unreachable.

Both of these are the same idea applied at different scales. Put the truth somewhere it can be checked, and say plainly what it does not yet establish.

# Dev Log - 2026-11-19

There is a particular kind of day in this repository where nothing looks wrong and something is still missing. The suite is green, the merges are clean, the diffs are reviewed, and a competent reader would sign off. And then someone asks a narrow question — on the path that actually executes, who checks this? — and the day's real work turns out to have been hiding behind a green checkmark.

That is what happened here, and it happened twice, in the same shape.

The first was technical and small. Yesterday's image work verified media signatures, required resolved paths to stay under the storage root, kept the `documents/` subtree behind its own account gate, and refused to dispatch when an image was genuinely unavailable. All of that was true and all of it was merged, and all of it was correct at the level of the service. The problem was that the queued worker's compatibility entry point never called the service at all. It had its own path, it did its own preparation, and it had none of the verification. So on the path where queued turns actually execute — the path production traffic takes — the media was still unguarded. A green test suite, because the suite was calling the service, and the service was fine.

I keep coming back to how small the fix is. Apply the same routing helper, after provider and model resolution, before every dispatch, including the rescue dispatches. That is the whole of it. And the whole of it came from a question that sounds almost pedantic: who verifies the media, on the path that runs? Pedantry at exactly the right altitude. The alternative was a green build and a hole.

The contract sentence that came with it is the part I would keep: *service-only invocation tests are insufficient proof of this boundary.* That is a general law of this codebase written down by someone who got bitten by it. A test proves that a function behaves. It does not prove that the function is called. Those are different claims and only one of them is about production. I have watched this repository learn that lesson repeatedly — in migration chains that were clean but not applied, in qualification receipts that were dated but not current, in a catalog that existed on both sides of a wire — and today it was written down in a contract file, which is where it belongs.

The second instance is the day's real work, and it is the opposite shape. Here the problem was not that something was missing but that two things existed. The slash-command catalog lived in the server as a set of chat intent IDs used to validate requests, and it lived in the React client as a catalog used to draw previews and scaffold text. Two copies, reconciled by hand, free to drift. Today one of them became the source: `guardian/slash_commands.py`, eighteen identities, published through two GET routes on the existing chat router, with a `manifestRevision` that is a hash of the canonical JSON so a client can tell a changed catalog from an unchanged one without guessing.

The contract that governs it is unusually good. Discovery performs no writes, no connector probes, no tool calls, no task dispatch. Responses are `private, no-store`. Both routes inherit the chat router's account-session and request-scope dependencies. Identity resolution is strict about the things that are usually sloppy: canonical tokens are reserved before aliases are indexed, a duplicate or a shadowing alias fails catalog validation rather than being quietly resolved, and `/project` is one record with both modes while `/workspace` keeps its own canonical identity instead of being an alias.

And then the sentence that gives the whole thing its shape: *discovery grants no execution authority.* Every record's availability in version 1 is `unknown`, with the bounded reason `eligibility_not_evaluated`, because a catalog read has no business deciding whether an account may act. It is tempting to make discovery smarter — evaluate the account, project eligibility, whether Obsidian is configured, return `available` — and every one of those temptations would have been wrong, because the moment the catalog starts answering "can you," it becomes an authorization surface, and it is a read-only GET route on a router that already has a lot of responsibility.

Then the day did the thing I actually think was brave. It took the most dangerous surface in the product — image generation, which spends money and calls an external provider — and made it *depend* on the new boundary rather than sidestep it. Image sends require a current, successfully loaded discovery entry with an implemented interaction mode. Missing discovery fails. Failed discovery fails. Explicit denial fails. `unknown` does not confer eligibility. And ordinary prose never reaches the adapter, including a passing mention of a visual style; you have to actually submit the command or confirm in the form. The whole design is a refusal to let a sloppy read turn into an expensive action.

And underneath it, a reconciliation nobody asked for: the image foundation had been sitting on a branch since the 17th, and the commit message says the work is to preserve that foundation — the provider adapter, the private-preview qualification, the modal lifted out of the composer — *on top of* the library that did not exist when the foundation was written.
