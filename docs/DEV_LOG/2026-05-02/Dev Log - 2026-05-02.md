# Dev Log - 2026-05-02

## Summary

A release-surface truth-alignment day. The work was not in new product capability — it was in making the things Codexify already claimed about itself either verifiable or correct. Three threads ran in parallel: the public beta handoff was hardened so a tester could get a working bundle without guessing, a public export path was added so a private repository could publish curated snapshots without broadcasting its history, and a weekly override of the release-truth document was rewritten into a shorter, more honest form that lost eight caution clauses along the way.

The through-line was the difference between a claim and a check. The beta handoff bundle gained a verifier that can bootstrap its own keys, confirm the env example is shaped correctly, and assert the archive does not contain a `.env` file. The media upload path stopped resolving URLs against the API base and started resolving them against the backend base, which is the actual bug that fix addresses. The export path gained a staging tree and a sync script. What did not happen was any runtime proof of any of it, and the day does not claim otherwise.

Eighteen commits carry this UTC day's committer date across all refs. Nine are ancestors of the fetched `origin/main` tip; the other nine are twin commits of the same subjects on a separate branch lineage, `origin/personal-facts-guardrails`, which is not an ancestor of main. The mainline work and the twin work carry byte-identical content for the public-export and campaign commits; the beta-auth pair differs only in whether the rebuilt beta bundle binary was included.

## What I completed

### The public beta handoff became a thing a tester could actually follow

Before this day, a tester receiving the beta bundle was told to copy an env file, and the env file's placeholder key was literally `replace-with-long-random-value`. The bundle's own instruction file now says how to generate a real key, where to put it, and how to tell whether the result is healthy.

- `Codexify-Beta/AUTHORIZATION.md` (113 lines, new) states what runs where — WebUI on `localhost:3000`, backend on `localhost:8888` — explains that the browser and backend must present the same `GUARDIAN_API_KEY`, gives the `python3 -c 'import secrets; print(secrets.token_hex(32))'` recipe, and names the exact health surfaces that must return `ok`/`healthy` afterwards.
- `Codexify-Beta/README.md` was rewritten from a four-step numbered list into a single "Normal flow" code block, with the key replacement made an explicit step rather than an implication, and a Linux/`open`-unavailable branch added so the instruction is not macOS-shaped.
- `scripts/release/package_beta_handoff_bundle.sh` now copies `AUTHORIZATION.md` into the staged bundle. The instruction existed but was not in the artifact testers received — the fix is packaging, not documentation.
- `docs/beta/README-FIRST.md` and `docs/beta/Private-Beta-Checklist.md` gained the matching checks: confirm the archive includes `AUTHORIZATION.md`, and confirm the tester was told to set the same key in both `GUARDIAN_API_KEY` and `VITE_GUARDIAN_API_KEY`.

### The handoff verifier stopped assuming and started asserting

`scripts/verification/check_beta_handoff_bundle.sh` grew by 77 lines, and the growth is almost entirely new assertions.

- `bootstrap_temp_api_keys()` generates a `secrets.token_hex(32)` key when `GUARDIAN_API_KEY` is unset, mirrors it into `VITE_GUARDIAN_API_KEY`, and rewrites both into a temporary `.env`. The verification run no longer depends on the operator having pre-seeded a key.
- `check_env_example()` asserts `GUARDIAN_API_KEY=` and `VITE_GUARDIAN_API_KEY=` are present and empty, that `GUARDIAN_DEV_MODE=true` is present, and that `GUARDIAN_CSP_POLICY` is quoted when it contains semicolons — the last one because an unquoted semicolon-bearing value is a shell-splitting hazard in a Compose env file, not a style preference.
- `check_archive_contents()` reads the built zip's listing and asserts it contains `README.md`, `AUTHORIZATION.md`, `docker-compose.yml`, and `.env.example`, and — the one that matters most — asserts it does **not** contain `Codexify-Beta/.env`. A bundle that ships someone's local env file is a credential leak, and the check makes that a build failure rather than a hope.
- The compose calls were given an explicit project name (`codexify-beta`) so verification cannot collide with a developer's running stack, and a `compose down --remove-orphans` runs before the pull checks so the verifier starts from a known state.
- `Codexify-Beta/.env.example` was changed to ship the empty-key-plus-dev-mode shape the new check requires, and `dist/Codexify-Beta-WebUI-local-beta.zip` was rebuilt to match (5,777 → 7,917 bytes).

### The media upload URL fix, traced to its actual cause

`frontend/src/hooks/useUploader.ts` had been resolving `/api/media/upload/image` and `/api/media/upload/document` through `resolveApiUrl()`. That resolver is correct for API calls and wrong for media uploads, and the difference is not cosmetic.

Reconstructing both resolvers as they stood at this commit and running them over three plausible runtime configurations isolates the defect:

- In the desktop/Tauri runtime, where `apiBaseUrl` is the relative `/api`, `resolveApiUrl()` returned the relative `/api/media/upload/image`. The upload then went to whatever origin the browser was on — the frontend's, not the backend's.
- Where `apiBaseUrl` was absolute and ended in `/api`, the resolver stripped the `/api/` prefix and re-appended it, producing the same absolute path. The bug did not appear.
- Where the API base and the backend base were genuinely different hosts, `resolveApiUrl()` sent media uploads to the API host and `resolveBackendUrl()` sent them to the backend host.

The fix routes the three media upload calls through `resolveBackendUrl()`, which unconditionally combines `backendBaseUrl` with the path. That is the correct base for a route that is served by the backend (`guardian/routes/media.py` registers `/api/media/upload/image` and `/api/media/upload/document`), and it is now correct in every configuration rather than correct in one. The frontend tests were updated to match: `gallery_auth.spec.tsx` and `uploader_document_auth.spec.ts` now assert against `resolveBackendUrl(...)` and `endsWith("/api/media/upload/image")` instead of an exact relative-string match.

### A public export path, so the private repository can publish without broadcasting itself

This was the day's largest structural addition and it is entirely new surface.

- `scripts/release/export_public_directory.sh` (220 lines) rebuilds a `Public-Directory/` staging tree from the private checkout. It copies the license, the beta bundle's README, `AUTHORIZATION.md`, `.env.example` and compose file, and generates a public README and `SECURITY.md` into a portal-shaped layout with `docs/public/{release-notes,install,security}` and `releases/Codexify-Beta`.
- `scripts/release/sync_public_directory.sh` (20 lines) copies that tree into a fresh repository path.
- `docs/release/public-portal-snapshot-workflow.md` (154 lines) states the contract: the private repo is the Source Vault, the public repo is the Publishing Portal, and the portal receives curated snapshots rather than a mirror of the working tree. It also states the intent directly — keep private work private, publish only stable snapshots, avoid broadcasting every edit.
- `Public-Directory/` was added to `.gitignore`, so the staging tree is deliberately untracked and rebuilt on demand. That is the mechanism by which the export stays a snapshot instead of becoming a second source of truth.
- `Makefile` gained `public-export` and `public-sync` targets, with `public-sync` requiring an explicit `target=/path/to/repo` argument and failing with a usage message otherwise.

### The weekly override was rewritten — and the rewrite lost things

`docs/architecture/00-current-state.md` was cut from 107 lines to 59. The new version is cleaner and more accurate in its headline claims: the phase is stated as "late beta hardening," the release definition is five unchecked boxes, and the priorities are five concrete actions rather than a wall of prose.

But the diff removed eight "Do not assume" clauses and added five more general ones. The removed clauses were the specific ones — the GHCR visibility caveat, the statement that backend-seam suites do not replace live Compose proof, the statement that the tool-loop proof does not close the broader gate, the Obsidian fixture caveat, the personal-facts caveat, the statement that delegation is excluded from the release promise, the internal-surfaces caveat, and the stale-proof caveat. The replacements were general: do not assume unmerged branch work is shipped, do not assume the webUI bundle replaces the Compose path, do not assume docs prove a surface is live, do not assume operator routes are in the promise, do not assume release readiness if the runtime posture has not been rechecked.

The `## Active blockers` section was dropped entirely, along with the `## What changed recently` narrative. Both were restored eight days later by `3b6355d70`, the next weekly override on 2026-05-10. The section structure at the fetched tip today still carries `## Active blockers` and `## Not yet true / do not assume`, so the shape the 2026-05-02 rewrite removed is the shape that stuck.

This is worth naming plainly because the same failure mode has a name now. On 2026-11-04, the weekly override `97f4194cf` replaced the Current phase and Not-yet-true sections wholesale and dropped two release-hold clauses the repo's own contract requires — the release gate said "is `HOLD`" instead of "remains `HOLD`", and the standing rule that capabilities without current-main qualification are not default Beta support was lost. PR #992 restored both, and `tests/evidence_packets/release_truth_contract.py` now exists to assert them. A weekly override that rewrites release truth wholesale is a recurring drift vector, and 2026-05-02 is an early instance of it.

## Important outcome

The day's real work was the conversion of assumptions into assertions, and the clearest case is the archive-content check. Before this day, the beta bundle's contents were a fact maintained by whoever remembered to update the packaging script — which is how `AUTHORIZATION.md` ended up documented but not shipped. After it, the archive's contents are a build-time assertion with a specific negative case: the absence of `.env`. A positive-only check would have been weaker; the thing that matters is that the check fails when a credential-shaped file appears in a public artifact.

The second structural shift is the separation of private development from public release. `Public-Directory/` is untracked, rebuilt on demand, and synced into a fresh repository path — so publishing is an explicit act with a defined payload rather than an accident of what the working tree happened to contain. The doc is explicit that the public repo is a snapshot, not a mirror.

The third shift is quieter and more consequential: the weekly override of the release-truth document was shown to be lossy. A shorter document that says "do not assume unmerged branch work is shipped" is better prose than a longer one that says "do not assume the Obsidian ingest→retrieve seam proof constitutes a full connector sync." The specific cautions are what keep a reader from over-reading a claim, and the rewrite traded eight of them for five general ones. The section came back on 2026-05-10; the contract test that would have caught the loss came on 2026-11-04. Nothing here proves the pattern was understood in May — it was simply not yet visible then.

## Closing thought

The measure of this day is not how much was added. It is how many places stopped depending on someone remembering. The key was in a zip listing, the export was in a `.gitignore` line and a Makefile target, and the URLs were in which base a resolver reached for. None of it looks like a release, and none of it should have been allowed to look like one.

What I want to hold onto is the override. The document got shorter and the cautions got more general, and for a while that read like an improvement. It was not an improvement; it was a trade that nobody had weighed, made quietly on a Tuesday by a script that was supposed to be refreshing truth rather than renegotiating it. The structure came back eight days later by accident of the next refresh, and the check that would have caught the loss came six months later. A truth document that gets rewritten wholesale every week needs a contract around it, and for most of this project's life it did not have one.

## Narrative Log

# Dev Log - 2026-05-02

This was a day of making the same claim twice and meaning it once. Almost nothing here added capability. What it did was take a set of things the project was already saying — the beta bundle works, the media uploads work, the release truth is current, the public can see the release — and check whether the artifact, the code, or the document actually agreed.

The beta handoff is where that shows most clearly. The bundle shipped a placeholder key and a README that assumed the reader knew the placeholder needed replacing. That is not a bug in the sense of a crash; it is the more common failure, where the instruction is technically present and practically unusable. The new `AUTHORIZATION.md` names the two ports, explains that the browser and the backend have to agree on one key, gives the command that generates it, and then says what healthy looks like in terms of three specific endpoints. The packaging script was changed to actually put that file in the zip, which is the part that matters, because documentation that is not in the artifact is documentation the tester never sees.

And then the verifier stopped being a viewer. The archive check is the piece I keep returning to: it reads the built zip's listing and asserts that `.env` is not in it. Not that the right files are present — that too, but the negative assertion is the one with teeth. A bundle is a thing that leaves your machine and enters someone else's. The checks that matter most about it are the ones about what must not be there, and until this commit nobody had written one.

The other thread was public release, and it was a different kind of problem. The private repository had been accumulating history that was never meant to be public, and the alternative to publishing was either publishing everything or publishing nothing. The answer was to stop treating publication as a property of the repository and make it a property of an act: build a `Public-Directory/` staging tree from a curated list, keep it untracked, and copy it into a fresh repository. The `.gitignore` entry is the load-bearing part. As long as the staging tree is untracked and rebuilt on demand, it stays a snapshot. The moment it becomes tracked, it becomes a second source of truth and the project has to maintain two of them.

The media upload fix is the one that took real work to characterize, and I want to be honest about how it was characterized. The commit says the URLs were wrong. The diff shows the base-URL resolver changing. The rest — why it was wrong, in which configurations it was wrong and in which it merely looked wrong — I reconstructed by re-running both resolvers as they stood at that commit across three plausible runtime shapes. In the desktop runtime the old resolver returned a relative path, so the upload went to the frontend's origin and never reached the backend. Where the API base was absolute and already ended in `/api`, the old code produced the correct absolute path and the bug never appeared. Where the two bases were genuinely different hosts, the upload went to the wrong one. That is the shape of it: the fix is correct everywhere, and the old behavior was correct exactly in the one configuration that looks like the common one.

The Pi campaign sits at the other end of the day, and it is worth being plain that it was planning. Four tasks, then three more tasks two minutes later, describing the same pipeline from the adapter protocol inward rather than from the envelope outward. The next morning the first adapter landed, following the second naming. Which brings up the thing I noticed while tracing it: both task sets are still on `main`, and both claim `TASK-2026-05-01-001`. The campaign document lists only the first set. So the decomposition that actually shipped is documented by a task file whose ID the campaign table does not reference. Small thing, but it is the kind of small thing that costs someone an afternoon later, and it cost me one to find.

The part I keep turning back to is the weekly override. It rewrote the release-truth document down from 107 lines to 59, and on the surface that was an improvement — the prose was cleaner, the phase was stated more directly, the priorities were five real actions. But the rewrite dropped eight specific cautions and replaced them with five general ones, and the specifics were the load-bearing part. "Do not assume the bounded tool-augmented completion proof closes the broader release gate by itself" is not the same claim as "do not assume release readiness if the live runtime posture has not been rechecked." The first one tells you exactly which proof you are looking at. The second one tells you to be careful. A document that only says be careful gets read as a formality.

What makes this worth recording rather than just noting is that the pattern was not a one-off. On 2026-05-10 the next override brought the sections back, and nothing flagged that the previous one had eaten them. On 2026-11-04 the same thing happened again — two release-hold clauses gone — and that time there was a receipt explaining it, a PR restoring them, and a contract test written so a weekly refresh could not quietly do it a third time. The `## Active blockers` section that 2026-05-02 removed and 2026-05-10 restored is, to this day, still in the document at the tip of `main`. The structure won in the end, and it won by outliving the particular mistake.

There is something in that I want to keep. The instinct on 2026-05-02 was correct: the release truth had become long enough to be skimmed, and a shorter document that a person actually reads is worth having. The mistake was assuming that shortening a document and changing what it asserts were the same operation. They are not. One of them is editing. The other is a decision about what the project is no longer willing to say out loud, and it deserves to be made deliberately, by someone who knows what was just dropped, rather than as a side effect of compressing a file.

So the day ends in an honest place. The beta bundle says what to do and the verifier checks what must not ship. The export path exists and is untracked on purpose. The media upload goes to the backend now. The Pi adapter has a name and a contract and a protocol to implement. The release truth is shorter than it was, and shorter was the right instinct, but it cost eight sentences of caution and took two more overrides to get them back — and it took a contract, written months later, to stop paying that price a third time.

What this makes possible next is straightforward: a smaller document that someone reads, with machine-checked sentences underneath it that nobody has to remember to write. That is the shape worth building. Not the shorter document alone — that one had already been tried, and it turned out to be lossy in ways that only show up months later.
