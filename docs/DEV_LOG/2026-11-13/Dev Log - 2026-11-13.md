# Dev Log - 2026-11-13

## Summary

2026-11-13 was a boundary day. Two large surfaces converged on the same underlying question: who, exactly, is acting on whose behalf? On the Guardian side, the accepted-chat account-custody boundary was decided, documented, implemented as a prerequisite, and carried into the command-bus readback path. On the client side, Scout stopped being a local-only convenience app and started behaving like a hosted client that must prove its account before it can read anything.

The Guardian work is the more consequential of the two, because it is the part that constrains everything later. ADR-112 accepted in-process Command Bus dispatch as the mechanism for the bounded GitHub/Notion read-only connector pilot, and it says the thing that matters in one line: the worker acts *on behalf of* an account; processing a job does not turn the worker into an account principal. Queue delivery is evidence of delivery, not execution authorization. Everything built on 2026-11-13 follows from that sentence.

The Scout work is the larger volume — close to 10,000 inserted lines across Swift, Guardian and tests — but it is mostly a client catching up to a server contract that already existed. The interesting part is not the line count; it is that the client-side transport, the Guardian-side widget serialization, the hosted Library reads, the project collection requests, and the design-token registry all landed in the same window, which is what a coherent client/server boundary looks like when it finally converges.

## Important outcome

The structural shift is that Codexify now has a written, accepted, and partly implemented answer to a question it had been answering by convention: **what makes an operation on behalf of an account legitimate?**

Before this day, the answer was spread across routes, queue payloads, and per-call site checks. The worker received a task; the task carried a `user_id`; the code that ran the task used whatever identity it could find. That is a workable heuristic and a poor boundary — it makes "who is this for" a question that different call sites answer differently.

After this day the answer has a shape. ADR-112 names the four authorities and says plainly what is not sufficient for each. The accepted-chat custody implementation makes the account a first-class persisted fact on the accepted attempt, with a migration that refuses to let it be quietly rewritten, that does not backfill history into a shape the history never had, and that keeps hosted-room and voice traffic explicitly outside the new scope rather than accidentally inside it. The command-bus readback enforces the same ownership on the read side. And the connector pilot that motivated all of it is deliberately still gated: `resolve_accepted_chat_account` is documented as an unconsumed prerequisite seam, because the honest state of the world is that the boundary has been decided and prepared but not yet claimed.

The Scout work is the visible half of the same idea. A hosted client that reads account-scoped Library documents, lists projects, and launches sandbox widgets has to prove which account it is on every request; the Guardian-side transport (`guardian/core/scout_account_transport.py`) and the media route's account-scoped pagination are what make that possible. The deployment receipt that records this — `docs/architecture/proofs/runtime/2026-11-13-saved-widget-library-scout.md` — lives on the `codex/saved-widgets-library-20261113` feature ref rather than on `main`, and it is explicit that installation and an empty authenticated list are not proof that the phone save/reopen interaction has passed.

## Closing thought

The honest characterization of 2026-11-13 is that a lot of authority got written down. ADR-112, the custody module, the migration's immutability rules, the readback ownership check, the account-scoped transports, the proof documents that say "this is not deployed or release-qualified" in their first paragraph — that is a lot of prose and a lot of schema, and on a day where the release gate did not move and no qualification surface became current, it would be easy to call it a slow day.

The system is being built so that the correct answer is the one it can prove, not the one that is convenient.

# Dev Log - 2026-11-13

The kind of day where nothing broke and the release gate did not move, and the work underneath was about something else entirely.

Most of the day's commits were about who is allowed to act. That sounds like a compliance topic, and it is not; it is the question underneath every feature that touches somebody's data. On 2026-11-13, Guardian got its answer written down for the first time in a form that can be checked. ADR-112 was accepted — an architecture decision with a human approver on it, scoped narrowly to a read-only GitHub and Notion pilot, and careful in its language to say that acceptance is architecture, not implementation, and not runtime proof. The sentence that carries the weight is this one: the worker acts on behalf of an account, and processing a job does not turn the worker into an account principal. Queue delivery is evidence of delivery, not execution authorization. I have read a lot of design docs that gesture at authority without ever pinning it down. This one lists four authorities — account identity, work ownership, connector permission, execution authority — and then, for each, names the thing that looks like it but is not sufficient. Possession of a job ID is not ownership. A previous successful read is not permission. An earlier attempt is not authority.

The implementation underneath it was careful in a way that is easy to miss. The accepted chat attempt gained a nullable account column, and the migration that carries it does no backfill, which means yesterday's rows stay NULL and stay ineligible for the new authority. That is the part I would defend hardest if anyone asked. It would have been easy — and tempting — to backfill and look complete. But backfilling would manufacture a custody claim for work that was accepted before anyone was tracking custody, and the whole point of the boundary is that it says something true. The migration also refuses to let a bound row be quietly rewritten, including the NULL-to-value transition, while still permitting terminal and tool-checkpoint updates, because those are the ones that move a row forward rather than rewrite its history. And it deliberately keeps no foreign key to the account, so deleting an account cannot cascade into erasing the record of who did what; instead the reader checks, each time, whether the canonical account still exists. That is the difference between a database that remembers and a database that merely stores.

Then the readback side, which is the half people usually skip. It is easy to fence writes and leave reads open. `guardian/routes/command_bus.py` now enforces the same ownership on the way out, with two test files that hold it, and three chat fixtures were rewritten to model a canonical owner instead of a convenient one. Fixtures are where architectural intent actually goes to die; three of them were changed today so that the tests could not pass by accident against a shape nobody intended.

The other half of the day was Scout, and it was larger and louder — a native conversation and document reader, an adaptive drawer and hosted account flow, interactive sandbox widgets with their own web session, hosted Library reads and previews, a shared design-token registry generating TypeScript and Swift from one source. Around eleven thousand inserted lines. The temptation is to describe that as the day's work, because it is what shows up in a diff. But what actually happened is a client catching up to a server contract, and the server contract is what makes it a client rather than an app. The Guardian side of that day — the widget serialization that had drifted, the account-scoped transport that admits project collection, the media route's account-scoped pagination — is the part that carries weight. A hosted client that lists your projects and reads your documents has to prove whose account it is on every single request, and the reason the client work looks coherent is that the boundary underneath it was already there.

There is one honest gap in all of this, and it is worth naming because the receipt names it too. The Saved Widgets deployment landed on the phone and the iPad, and the hosted web Library showed the right view with an empty list and no API error. But launching Scout from Xcode tooling was denied because the phone was locked, and Device Hub cannot inject taps into a mirrored phone screen.
