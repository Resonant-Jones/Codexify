## Important outcome

The day's structural shift was in the definition of a proof. The old backup script treated the running system as something it could stop and rebuild on demand — freeze by Compose service name, restore by Compose service name — which is a reasonable assumption right up until the moment a restart produces a container with a different identity, or a reconciler brings the environment back mid-proof, and the thing you were trying to demonstrate is no longer the thing you are talking about. The rewrite inverts the relationship: capture the exact identity of everything first, verify the serving checkout against a pin, refuse to proceed if an external reconciler is in flight, and on the way out restore by container ID and *prove* the inventory came back identical — failing loudly when it did not. A proof that can alter what it measures, and cannot tell you afterward whether it did, is not a proof. This one can.

The recovery checkpoint that landed alongside it is the other half of the same discipline, and its quality is in the parts most receipts would leave out. The dump and archive were verified by two independent paths — `pg_dump`'s own exit and an external `shasum -a 256 -c`. The census and the dump were bound to the same snapshot via `pg_dump --snapshot`, so the counts describe the bytes actually archived rather than a separate, later read. The restore was run with network mode `none` and no production mounts or credentials. The six pre-existing thread-to-Project owner mismatches are named, and the scope section says plainly what the checkpoint does not cover. It also records its own failed attempts and the fact that the successful retry verified recovery at the PostgreSQL boundary while the application image and mounted source still had mixed identities.

What links these two is a boundary the codebase has been learning to respect all month: the difference between a claim about a *system* and a claim about a *database boundary*. The receipt is explicit that it verifies the latter. It does not prove a coherent application deployment, and it does not say it does.

The other mainline artifact exists because of exactly that kind of ambiguity, and it is the reason the checkpoint was possible at all. The old backup/restore proof script assumed it could freeze the Preview by stopping Compose services and then rebuild it by naming those services again. That assumption is reasonable right up to the moment it is wrong — when a restart produces a container with a different identity, or a reconciler brings the environment back while the proof is mid-flight, or the source that was serving has drifted from the source the script thinks it is inspecting. At that point the proof is not describing a system any more; it is describing its own memory of one.

The rewrite inverts the relationship. Before touching anything, it captures the full container inventory — every container's ID, image, service, running state, restart policy, mounts, ports, networks, Compose config files, working directory and config hash. On the way out it restores by exact container ID and then compares the post-restore inventory against the pre-run one, byte for byte. If they do not match it fails with "Original inventory could not be restored exactly. Manual recovery required." That is the whole change in one sentence: the proof no longer restores a *description* of the environment, it restores the *environment*, and it proves it did.

Around that sit a set of smaller refusals, and refusals are what make a proof trustworthy. It will not run if the pinned serving source is the development checkout. It will not run if the serving checkout has tracked changes. It drives Compose from the pinned overlays rather than the repository's own files. A reconciler gate runs before the freeze and checks `launchctl` state, failing closed on an ambiguous response — because on this host a background reconciler bringing the Preview back mid-proof is not hypothetical. Cleanup became defensive too: the restore container and volume are removed only after their identity and their `codexify.checkpoint` label match, and left in place if they do not. The media restore directory moved under the checkpoint directory so that cleanup cannot reach outside its own scope. The signals changed so that an interrupted proof still runs its restore path. And the database side got `PGOPTIONS='-c default_transaction_read_only=on'`, so a proof that says "read only" enforces it at the session rather than trusting the script's good intentions.

The database opens a named cursor with `itersize = 128` and hands rows to a writer callback as they arrive, under a `REPEATABLE READ READ ONLY` transaction so the streamed rows and the metadata rows come from one snapshot. The service side stopped building body bytes entirely: JSON payloads are written into the archive incrementally while the SHA-256 is computed over the same byte stream, blobs are staged to a temp file and copied through `shutil.copyfileobj` into a `force_zip64` member.

The detail I like most is a quiet fix to a bug that would have bitten someone months later. Media is now deduplicated by canonical blob key rather than by asset ID. Two rows pointing at the same bytes produce one archive member and one shared `bundle_path`. That matters because a ZIP with duplicate member names cannot be restored — so the old behavior was not just wasteful, it was producing archives that a restore would reject. The new test asserts exactly that: one member per distinct blob, unique names across the whole archive, and a manifest whose per-file digests and byte lengths still verify. And ownership is enforced before anything streams: if a project in scope belongs to another account, the export raises and writes nothing, and the test asserts the cursor is never opened.

The Campaign Engine preflight is the opposite end of the scale — no code at all, 334 lines of reading, and it found something a code review would probably have missed. The role callables accept a supplied envelope and decision. The common invocation boundary checks structural agreement and the `allowed` flag. But it does not resolve trusted issuance, authoritative custody, expiry, revocation, or durable consumption before dispatch. The preflight names the exact transition where that matters: prepared role input → trusted Guardian-issued authorization, at `invoke_guardian_authorized_pi` lines 270-280, where a successful structural check plus a caller-supplied `allowed` is treated as sufficient to proceed. Structural agreement establishes that two objects agree with each other. It cannot establish that an authoritative current decision exists anywhere.

What I respect about the preflight is how it handles the thing it could not find. It looked for a separate output file across all 103 registered worktree entries, in `.worktrees/*`, in both managed worktree roots, and in `git log --all -- <path>`, and found zero matches — then said so in exactly those terms: absence within that search, not deletion and not nonexistence everywhere. That is the correct epistemic status, and it is now out of date in the most literal way: a later commit `d5e418aad` creates precisely that file, with a committer date of 2026-11-13 01:46 UTC. It belongs to the next day's log, not this one, but it means the preflight's careful "not recovered" should be read against a document that now exists on a branch.

The fixture reproduction is the third, and it is the most satisfying because it is an explanation rather than a verdict. One hundred and twelve tests, one passing, 111 failing. The receipt reproduces it: before LFS hydration, 112 collected, 1 passed, 111 failed, exit 1. After a path-bounded `git lfs fetch` and `git lfs checkout` hydrated 17 of 17 files, 112 collected, 112 passed, exit 0. In 108 of those failures the JSON trace displayed an LFS pointer. The suite was not broken. The files were not files yet. And the receipt keeps the limit visible: `git lfs fsck` passing *before* hydration confirms cache integrity, not working-file hydration, and the full backend suite was not run.
