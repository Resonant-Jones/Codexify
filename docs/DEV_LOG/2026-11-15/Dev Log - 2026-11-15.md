## Summary

2026-11-15 was the day the release gate stayed put and the reason became precise. Four consecutive `Guardian CI` pushes on `main` were red — `410305fb4`, `2c6ede123`, `dee854aaa`, `3e667a6ab` — and all four failed on exactly one assertion: `tests/qualification/test_qualification_registry.py::test_committed_registry_is_current`. The release-truth document already called this the fourth consecutive red; by the end of the day it was the sixth. The cause was not flaky, not environmental, and not a coincidence of unlucky merges. It was structural: the qualification registry is a projection whose inputs are the repository's changed paths, so every merge that touches a path inside a qualification surface's scope moves the projection, and the committed registry has to be regenerated against the *merge tip* or it is stale by construction. The refresh in `58c93d5de` had been computed on a PR branch head where it matched exactly. The merge onto `main` then brought in further `frontend/**` files from two merges that landed alongside it, and the projection moved from 157 changed paths to 163 on `supported-compose-stock`. The committed registry did not move with it.

The rest of the day was a counter-pattern: three genuinely important correctness fixes, all on feature refs, none of them yet mainline by the time the day closed. The voice pipeline gained real account ownership — not an admission check at the edge but an authority re-check carried through the worker's processing waits, so a turn cannot complete on a thread the caller has since lost. The account import service stopped deleting staged blobs on an ambiguous commit, which was destroying recoverable bytes during exactly the failure it was supposed to survive. The Deepgram STT request stopped multipart-encoding prerecorded audio it had already in raw form. And a Guardian Inspector landed on a branch that lets an account see the newest *durable attempt* rather than the newest available capture — with an acceptance-evidence timestamp that is explicitly allowed to be absent, because a missing record cannot distinguish enqueue failure from a recording failure after a successful enqueue.

The honest shape of the day: the mainline surface movement was small, the correctness work was substantial, and the one thing that would have made the day green — regenerating the registry against the merge tip — did not happen until the next merge, hours after the day closed.

### Import staging stopped destroying recoverable bytes (mainline)

- **`c72e87e38`, merged as `#1086` (`3e667a6ab`)**, is a small, careful change to `guardian/services/openai_account_import.py` — 91 lines changed, 272 insertions / 67 deletions with the tests.
- **The bug was that failure recovery deleted the data it was meant to protect.** The previous code uploaded each addition, and on *any* exception rolled the transaction back and deleted every uploaded storage path. But a commit exception can leave the manifest durable — the transaction may have landed even though the commit call raised. Deleting the blobs in that case destroys bytes for a manifest that actually exists, turning an ambiguous commit into permanent data loss. The fix separates the two concerns: the write loop no longer deletes on failure, because a failed write leaves the manifest transaction uncommitted and a retry can reuse the same storage names; and the `session.commit()` now stands alone, because once it returns, a later refresh or serialization error only affects the reply. The comment in the code says exactly this: *"A commit exception can leave the manifest durable. Once commit returns, any refresh or serialization error only affects the reply."*

The tests are written to distinguish a pre-commit failure from a post-commit error, because the whole fix lives in that distinction.

## Important outcome

The structural shift on 2026-11-15 is that the repository learned to describe **which projection a claim is computed against** — and to show the drift in the artifact rather than only in a CI log.

The qualification registry is a projection of repository evidence onto qualification surfaces. That makes it structurally fragile in a way most generated files are not: it is correct only against a specific revision, and *merging is itself a change to the repository*, so a registry generated on a branch head is stale the moment the branch merges. The day proved this the hard way, with six red pushes on one assertion, and the release-truth document named the mechanism in advance: the refresh had matched exactly on the PR head; the merge moved `supported-compose-stock` from 157 to 163 changed paths; the committed registry did not move with it.

What matters is that the failure mode is *legible* rather than mysterious. The committed registry carries its own blocker strings with the exact path counts. The assertion names the tip it disagrees with and the command that fixes it. The surfaces' `PASS`/`stale` and `HOLD`/absent statuses did not move and did not pretend to. A reader can tell the difference between "this surface was qualified and the code has since changed" and "this surface has never been qualified" without inferring it from a red build. That distinction was already in the design; the day is what proved it holds under repeated merges.

The second half of the shift is on the feature refs, and it is a pattern rather than a feature: **each fix narrows what the system will do when it is uncertain**. The import service no longer deletes bytes because a commit was ambiguous. The voice worker no longer completes a turn because access was valid at admission. The Deepgram client no longer assumes a multipart wrapper for bytes it already holds. The Inspector no longer calls a missing acceptance record a rejection. Four different subsystems, one direction — ambiguous state now produces less action and more honesty about what is known.

The branch's answer is to re-check authority at every point where the turn would otherwise produce a side effect: before the upload is even read, after the normalization wait, after the turn completes, before a cached asset is returned, before the asset is written, and inside the worker before a token is published or a result is persisted. A missing binding is a security gap; a deliberately-absent binding in single-user local mode is a supported mode. Merging those two into "no account" would have made the local compatibility test indistinguishable from a bypass, and the fix costs one field and one comment to keep them apart.

The Deepgram change is the smallest and, to me, the most satisfying. Move `Content-Type` into the headers, move the model parameters into the query string, and post the bytes as the body. Nothing about this is architectural. It is the entire reason the request was failing, and it was failing for a reason that had nothing to do with the provider.

And then there is the Guardian Inspector, where the interesting part is a correction. The first commit built an account-scoped view of the newest turn, and its route docstring said it selected "the newest durable completion". That was wrong, and the second commit fixed it, because the durable attempt is persisted *before* the task is enqueued — which means the newest attempt can be one whose enqueue failed. So the endpoint now selects the newest durable *attempt*, and it exposes `accepted_at` separately, with a comment that is worth quoting for how precisely it refuses to overclaim: *"This durable timestamp is positive acceptance evidence only. A missing record cannot distinguish enqueue failure from post-enqueue record failure."* Absence of a timestamp is not evidence of rejection. It is unconfirmed. The UI shows acceptance evidence separately from capture availability and never skips an unconfirmed latest attempt in favor of older captured work. That is a small, careful distinction, and it is the difference between an inspector that reports what happened and one that reports what it wishes had happened.

The Space game proof is the day's most cheerful artifact and also its most disciplined. Signal Relay runs anonymously from a link; a guest may share their Codexify display name with the open game page, once, with a nonce, a two-minute expiry, and — the part I like — *no redeemable grant*. The name lives in the open document. Reload clears it. An unset display name leaves you as Guest. And the README's scope sentence is exactly right: *"This establishes no production Space admission or release support."* It also tells you how to check it yourself: compare the bytes of all three game files at both origins, decline a request, approve one with a test account, confirm each approval calls the display-name endpoint exactly once and that no profile call precedes approval, and repeat from an origin that is not on the allowlist to confirm the Vault blocks it. A proof that tells you how to disprove it is worth more than one that only tells you it passed.

Now, the other half of the day, which is the half that made the build red.

The registry is a projection. It takes repository evidence and projects it onto four qualification surfaces, and the result is checked into `docs/qualification/registry.json` and then diffed against a fresh projection on every push. The problem is structural and almost elegant in its cruelty: the projection's inputs include the changed paths of the repository, and *merging is a change to the repository*. So a registry generated on a branch head is correct about the branch and stale about the merge. The refresh in `58c93d5de` matched exactly on its branch. The merge onto `main` then brought in further frontend files from two merges that landed alongside it, and the `supported-compose-stock` changed-path count went from 157 to 163 — and the committed registry did not go with it. I verified those counts myself against the committed registry at both revisions rather than taking the release-truth document's word for it; by the tip they stood at 169 and 62. Six pushes went red on one assertion, `test_committed_registry_is_current`, and the assertion was unusually helpful: it named the tip it disagreed with and printed the command that would fix it. The `pull_request` runs of those same branches were green, every time, which is the tell.

And here is the thing I want to be careful about, because it is easy to misread this day. It is tempting to say: the release-truth document got the red-streak count wrong — it said "fourth consecutive red" when the day ended at six. That is true, and it is a detail: the document was written during the day, before the last two runs had concluded, and a release-truth document is a snapshot by construction. But the more interesting observation is the one about the artifact's *content*. The registry carried its own blocker strings with the exact path counts. The surfaces did not move and did not pretend to: `PASS` but `stale` for the two that had receipts, `HOLD` on absent evidence for the two that did not, and the difference between "qualified once, code has changed since" and "never qualified" stayed legible without anyone having to read a red build log and reason backwards about what it meant. That separation survived six consecutive failures without degrading. I would rather have a system that fails loudly and keeps its categories honest than one that passes and conflates them.

Which leaves the thing I actually want to carry forward. Every one of the real fixes today — the import service, the voice worker, the Deepgram client, the Inspector — is a decision to do *less* in the presence of uncertainty. Not delete the bytes, because you cannot prove they are uncommitted. Not complete the turn, because you cannot prove access still holds. Not call the absence of a record a rejection, because you cannot distinguish the two causes. And the registry, for all its red builds, is doing the same thing from the other side: it is refusing to describe a repository state it has not been computed against. It failed loudly instead of lying quietly.

That is the through-line, and it is worth stating plainly because it is easy to believe the opposite about a repository in this shape: the code here has a strong instinct toward cautious refusal. Every branch I read today ended in a comment explaining what the system will *not* claim. The gap is not in the artifacts' honesty. The gap is that a truthful artifact can still be a stale one, and nobody ran the regeneration at the merge rather than at the branch. That is a missing step, not a missing virtue — and missing steps are the cheapest thing in this repository to fix.

Which is where I want to leave the day. Not with the six red builds, but with the fact that the day's work made the system more careful about what it asserts, and that the one thing standing between that care and a green build was a single command run at the right moment.
