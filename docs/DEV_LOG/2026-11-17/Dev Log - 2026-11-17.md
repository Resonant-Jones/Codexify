## Important outcome

The day's structural shift is that **authority stopped being a thing you check and then hold, and became a thing you re-resolve at the moment of the side effect.**

Until this week the pattern across the codebase was admission-time authorization: a request arrives, the caller is checked against the route's rules, the work is queued, and the authorization is carried forward as part of the task. That pattern is fine for synchronous work and quietly wrong for anything that spans time, because authority can be revoked between the check and the effect. The accepted account-bound Knowledge read is the clearest expression of the new position. It freezes exact task evidence, then re-resolves persisted original and current account ownership, acceptance, terminal state, cancellation, the accepted deadline, the current OAuth generation, expiry and the selected repository — at every execution boundary. Current placement or queue fields cannot select a new accepting account. Missing, legacy, conflicting or stale authority fails closed. The OAuth generation is the elegant part: a refresh claim, a refresh completion, a reconnection or a repository reselection invalidates the old generation, so a connection cannot be silently re-pointed at different content and then replay its earlier evidence.

The same position appears in three other places today, and it is worth noticing that they were built independently, which is what makes it a position rather than an incident. Lens invocation captures persona selection under the admission lock and rechecks it atomically at persistence, and refuses to parse display names or message text to do it. The private profile readback binds account fields to a fresh task-scoped authentication rather than to the ambient session. And the imported-recall candidate, which is the most ambitious of the four, has no registration path at all — it is a module with no route, no command, no enable switch, so the capability cannot be reached by accident.

What this makes possible is narrower than it sounds and more valuable. It does not make anything shippable — the release gate is `HOLD` and both `PASS` surfaces are `stale`. What it does is make the *next* thing safe to ship, because the authority model underneath it is now re-checked rather than assumed, and because the failure path is written down: denied replays are distinct events, partial results are never persisted, audit-storage failure prevents dispatch rather than following it, and unsupported program markup is omitted with a notice rather than half-rendered.

Nine times over, the shape was the same: a capability that used to be guarded by a check performed once at the door became guarded by an authority that is re-resolved at the moment the side effect happens.

The clearest instance is the accepted account-bound Knowledge read, and it is worth following closely because the reasoning inside it is the reasoning of the whole day. The existing Command Bus already had custody. What it did not have was a way to make sure the custody it held was still the custody that applied. The new module, `accepted_knowledge_read.py`, freezes the exact task evidence and canonical arguments, and then — at every execution boundary, not once at the start — re-resolves the persisted original and current account ownership, the acceptance, the terminal state, cancellation, the accepted deadline, the current OAuth generation, expiry, and the selected GitHub repository. Current placement or queue fields cannot select a new accepting account. Missing, legacy, conflicting or stale authority fails closed.

And then there is the OAuth generation, which I think is the most elegant thing built today. `read_grant` reads authority *metadata* without decrypting credentials. Credential resolution happens just in time, bracketed by revalidation, with no ambient fallback and no automatic refresh. And a refresh claim, a refresh completion, a reconnection, or a repository reselection invalidates the old generation. So if you reconnect to a different repository, the evidence you gathered against the old one cannot be replayed against the new one. The generation is not a timestamp; it is a promise that everything downstream of it was gathered under the same conditions it was authorized under. That is a small idea and it does a lot of work.

The refusal list in that same document is as careful as the happy path. Caller-supplied account claims, headers, provenance, idempotency identity, target URL and work-order linkage do not supply authority — server-derived actor and lineage replace them. The trusted caller has to hand in an explicit server-resolved permission profile plus external policy rules, because OAuth consent alone is insufficient. A profile must authorize the specific account, the specific task, the specific thread, the exact read, network use and connector use. Fixed-host external allow rules are mandatory and deny rules prevail. The lane accepts exactly two operations, GitHub and Notion `content_search` and `content_read`, with one specific manifest tuple. Missing or altered manifest entries fail closed. A denied replay appends a `run.blocked` event with `phase=replay` and returns no result — it does not rewrite the original execution's completed status, because a failed replay is not a failed original. Failures and cancellation persist no partial provider result. Audit-storage failure prevents dispatch instead of following it.

And the boundary that matters most: `execute_accepted_knowledge_read` has no HTTP route and no chat caller. The production Preview app still omits provider-operation routes, and this implementation neither mounts them nor fabricates the missing manifest entries. The synthetic test app includes the real operation routers solely so the manifest can be proven, and HTTP authentication is never bypassed or impersonated — not even in a test, which is exactly the place where that shortcut is most tempting and most corrosive. The document names the owner for the chat tool-loop handoff and stops there. I like that it stops there.

There is a smaller version of the same discipline in the imported-UI work, and it is my favorite commit of the day. The problem: exported ChatGPT-style messages contain `{@body ...}` program markers, and the frontend has to decide what to do with them. The tempting implementation is a parser — find the marker, read the program, maybe render it. The commit instead locates the *end* of the marker with a hand-written brace scanner whose docstring says, in full, "This is deliberately not a JavaScript parser. Ambiguous regex/template syntax, an unterminated construct, or the scan budget fails closed to the message end." A backtick returns the end of the message. An ambiguous slash returns the end of the message. If the scan budget runs out, it returns the end of the message. So a program-bearing paragraph gets omitted with an explicit notice instead of being half-rendered, and static content in the same paragraph may be omitted too rather than the scanner guessing where the program ended and the prose resumed.

The whole layer follows the same rule: the scanner never evaluates JSX expressions, never mounts arbitrary HTML, never spreads source props, never fetches resources, never invokes the generative-UI host bridge. It caps trees at 32,768 characters, 512 tokens and 20 nesting levels. It inspects at most 32 literal attributes and uses only fixed presentation properties. Images become placeholders. Links reject non-HTTP(S) schemes, credentials and control characters. The neutral label "Reconstructed display" is chosen deliberately, because it does not assert import provenance — the system says it reconstructed something and stops there, without claiming to know where it came from.
