# Dev Log - 2026-05-03

## Summary

A contract-hardening day, with a second track running underneath it. The delegated coding path stopped being a route that merely implied work would happen and became an explicit boundary: a typed task, a queue entry, a named worker, and an auditable return path into the thread that asked for it.

Underneath that, the product surface moved — model-override editing in the chat composer, voice selection and playback metadata, uploader authentication alignment, and assistant audio moved to lazy load — and a substantial truth layer landed alongside it: the agent protocol operations index, the solo-operator coding-worker runbook, the web-agent retrieval boundary spec, and a 31-file backfill of the daily blog archive.

## What I completed

**The delegated coding path became a real boundary**

- `PiCodexRunnerAdapter` landed as a concrete execution target in `guardian/agents/adapters/pi_codex_runner.py` (133 lines), registered in the adapter registry, so Guardian had something to dispatch to rather than an implied capability.
- `POST /api/agents/coding/execute` was added to `guardian/routes/agent_orchestration.py` (router prefix `/api/agents`, mounted from `guardian/guardian_api.py`). It accepts a `CodingAgentTaskEnvelope` per ADR-020 and opens a deployment-scoped flow id of the form `coding_<coding_task_id>`.
- The route stopped executing inline. `CodingExecutionTask` was added to `guardian/tasks/types.py` under the `coding_execution` task type, carrying `run_id`, `deployment_id`, `instructions`, `cwd`, `timeout_seconds`, `coding_task_id`, `attempt_id`, `thread_id` and `source_message_id` — the lineage fields the return path depends on.
- `guardian/workers/coding_worker.py` (215 lines) and a `coding_execution` registration in `guardian/queue/redis_queue.py` put a consumer behind that task. The orchestration route shrank accordingly (55 lines changed, 39 removed) because the route no longer owned execution.
- Result ingestion landed in `guardian/agents/store.py`: `store_coding_result` writes a claim and injects a `coding_result` message into the source thread, guarded by an existing-message check on `(thread_id, extra_meta.run_id, kind == "coding_result")` so a repeated delivery does not produce a second result message.

**Local composition and operator surface**

- `TASK-2026-05-03-001` was written as the live compose proof task (264 lines), covering enqueue, dequeue, terminal state, event lifecycle and duplicate prevention — the shape of the verification the code was asking for.

**Model authority at the call site**

## Important outcome

The delegated coding path stopped pretending to be synchronous. It now has a typed task, a queue entry, a named worker service, and a return path that writes a claim and injects a single result message into the originating thread with run lineage preserved.

That is the real shift of the day. Not that a feature appeared, but that implicit behavior became an expressed contract — in code, in the compose topology, and in operator documentation. Three places that can now be checked against each other instead of inferred from each other. The idempotency guard on result injection is the clearest example: duplicate delivery is now a condition the code names, rather than a bug waiting to be rediscovered.

## Narrative Log

It was a contract-hardening day, and the through-line was stopping the system from implying things it had not actually committed to.

The first correction was at the execution seam. `PiCodexRunnerAdapter` gave Guardian a concrete execution target, and `POST /api/agents/coding/execute` gave it a way in. On its own that would have been a thin addition — a new endpoint doing work synchronously inside a request handler, exactly the kind of thing that looks like a feature and behaves like a trap. The interesting decision was the one that came next: taking execution out of the route and putting it behind a typed `CodingExecutionTask`, a `coding_execution` queue entry, and a `coding_worker` that consumes it. The route got smaller as a result. That is the tell — when a boundary is real, the thing on the wrong side of it usually shrinks.

The second correction was on the way back in, and it is the part I trust most. Result ingestion into `guardian/agents/store.py` writes a claim and injects a `coding_result` message into the thread that asked for the work, carrying `run_id`, `source_message_id` and `thread_id` so the answer can be traced back to the question. The guard that checks for an existing `coding_result` message on the same thread and run is small, but it is the whole point: the system now names duplicate delivery instead of quietly tolerating it. A pipeline where the return path is linked to the origin by identifiers is a pipeline someone can audit after the fact.

The third layer was operational truth, and it is the layer most likely to rot if neglected. The protocol operations index, the solo-operator coding-worker runbook, the live compose proof task, the web-agent retrieval boundary spec — these are not commentary on the code, they are a second expression of it that can disagree with it. The value is not that they are correct today. The value is that when they stop being correct, there is a written claim to check the code against.

Around all of that ran a second, more ordinary stream of work: model-override editing so model authority could be chosen at the call site, voice selection and playback metadata, uploader authentication aligned with thread selection, and assistant audio moved to lazy loading with three lines removed from the worker as a result. And a 31-file backfill of the blog archive, plus a lockfile consolidation big enough to be invisible in a review — roughly 4,800 lines leaving the root lockfile — that is exactly the kind of change nobody notices until it is the only thing standing between you and a broken install.

Two things from the day deserve to be named plainly, because they are the kind that does not announce itself. One commit's subject line describes a different change than the one it carries; the architecture index it claims to add arrived in two other commits, and what it actually shipped was an archive backfill plus frontend environment and test-config changes. Subject drift is small and it is also how a day's history becomes unreconstructable six months later. And the same logical work was committed twice — once on the mainline, once on a parallel feature ref — so there are now two copies of the same truth, and only one of them is shipped reality. Both are cheap to fix now and expensive later.

What changed underneath is worth stating without inflation. The system stopped describing delegation as if it were a function call and started treating it as a distributed boundary: request in, run created, task queued, worker picks it up, result returns through the same thread that asked, lineage intact. That shape can be proven. The previous shape could only be believed.

So the honest position at the end of the day is this: the pieces are assembled, the names are in place, the docs describe what the code says the pieces do. None of that is live runtime proof. The compose proof task was written that day; the run was not. The idempotency guard was implemented; it was not exercised under retry. The lane was merged and structured, not qualified. Everything after that — the queue behaving, the worker heartbeating, the result arriving exactly once — is a question for the next run, and the next run's job is to answer it against the system rather than the design.
