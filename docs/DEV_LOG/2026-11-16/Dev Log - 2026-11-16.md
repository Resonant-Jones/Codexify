## Important outcome

The structural shift on 2026-11-16 is that the repository learned to **separate the liveness of a pipeline from the posture of a release, and to make that separation executable**.

Yesterday's lesson was about projections: a truthful artifact can still be a stale one, and the gap between "correct about its inputs" and "current" is where six builds went red. Today's lesson is adjacent and is about sentences. The release-truth contract does not merely require the document to say `HOLD`; it requires the document not to claim greenness anywhere else, because a document that says "main is green" and "the release gate remains HOLD" is not a nuanced document — it is a contradictory one, and a reader who skims the first line gets the wrong answer.

The mechanism is worth stating because it is precise. `release_truth_contract.py` already knew how to distinguish an artifact claim from a posture claim: "the release checklist is release-ready" is allowed; "the release is ready" is not. It applies the same distinction to `` `main` `` — with an explicit guard so that "the main documentation is release-ready" stays narrow — and it treats `green` as a readiness predicate. So a single phrase in a blockers section was enough to fail two workflows. The sentence that replaced it, "the tip's `Guardian CI` run is green", is *more* precise and *equally* true, and it carries a different meaning: a fact about one pipeline at one revision. Nothing was softened to make a test pass. The claim got narrower because the narrower claim was the true one.

That is the same instinct the rest of the day kept showing, approached from the other direction. The chunk service does not create a new import status. The repair service does not confer account authority. The inspector projects text leaves and fixed metadata, and explicitly refuses to return the raw body. The proposal grants no runtime authority. The Lens preflight requires the voice panel to fail truthfully rather than substitute a catalog entry. Every one of these is a decision to let the system say less than it could.

And the day's other structural move runs the opposite way — from careful to complete. The registry drift is closed, the six-push streak is over, and the fix landed where it had to land: inside the merge. The proof that this was structural rather than lucky is the tip's own green run, which executed the backend suite and passed the drift assertion at the tip.

## Closing thought

The day came down to two sentences.

In the morning, one sentence said the release gate is `HOLD` and the registry's projection is current against the tip, and both were true, and the build was green because a refresh had finally been computed against the tree it describes. In the afternoon, another sentence said `main` is green, and the repository refused it — not because green was untrue, but because the sentence had claimed more than it knew. The fix was to say the narrower true thing: *this pipeline, at this revision, is green*. The release gate is still `HOLD`. It was still `HOLD` while the pipeline was green, and it will presumably be `HOLD` when the pipeline is green again, and a document that blurs those two things is a document that will eventually be wrong in the direction that matters.

What I keep coming back to is how cheap the repair was and how expensive the detection was. One line of prose, ten minutes, two workflows back to green. But the detection took a weekly doc refresh, and that refresh was going to happen eventually, and the sentence that broke it was written by someone making an accurate observation — the drift really was closed, `main` really was green — and the observation was still a release claim. That is what I want to remember about today: the error was not carelessness. The error was a true statement carrying a false implication, and the repository happened to have a test for exactly that, which is a genuinely rare thing to own.

## Narrative Log

# Dev Log - 2026-11-16

A day that opens with the build going green for the first time in a week and then, seven hours later, goes red for a reason nobody would have predicted: the release-truth document was too cheerful.

Let me start with the green, because it is the concrete thing and it is the thing yesterday's log had been asking for. Six consecutive pushes had failed on one assertion — the committed qualification registry no longer matched a fresh projection of the repository, because merging is itself a change to the repository and a projection computed on a branch head is stale the instant that branch merges. Yesterday's log put it plainly: a truthful artifact can still be a stale one, and the gap between those two states is where six builds went red. The fix was never "regenerate again." The fix was to compute the projection at the merge result instead of at the branch, so that the number and the thing it describes arrive together.

That is what happened. PR #1087 carried the voice work — account ownership through the voice pipeline, and a correction to the Deepgram request that had been wrapping raw bytes in a multipart envelope for no reason at all. And inside that same PR, `0ec22f801`, was the qualification refresh, computed against the tree that was about to land. The merge went green at 02:23 UTC with every job passing, including the container migration job that had been skipping itself for days because its backend dependency kept failing. `main` was green. Not "the drift was closed" green, not "the assertion would pass next time" green — green, at a named revision, with the full job matrix run.

And the voice work itself deserves a moment, because it is the third day running that the same instinct shows up. The problem with account ownership in an asynchronous pipeline is that admission and completion are separated by time. The request arrives, you check the caller may touch this thread, you enqueue the work — and then the voice turn reads audio, normalizes it, waits on a provider, streams tokens, synthesizes a reply. Across that span, the caller's access can change. So authority is not checked once at the door and then assumed; it is re-checked at each point where the turn would otherwise produce a side effect. Before the audio is even read. After the normalization wait. After transcription, before the result is stored. On every streamed token. On cancellation. A turn admitted under authority that was later revoked stops, instead of completing on someone else's thread.

The detail I want to keep is the one that looks like a no-op. `VoiceTurnTask` carries an `account_id` whose `None` is explicitly the bounded local legacy lane, not a missing remote binding. A missing binding is a security gap. A deliberately absent binding in single-user local mode is a supported mode. Merge those two into "no account" and the local compatibility test becomes indistinguishable from a bypass — you could no longer tell, from the test output, whether the security check ran. So the field stays, and the comment stays, and the test is parametrized over both lanes: `local` and `account`. It even caught a bug in its own fixture while doing it. The disposable-PostgreSQL setup was calling `alembic upgrade` before setting `DATABASE_URL`, and Alembic prefers the environment variable over its config — so the test had been migrating the wrong database. Running the same test in two lanes is what surfaced that. A one-line comment, a reordering, and a real fix to a test that was quietly not testing what it claimed.

Then the day turned. At 10:12 UTC the weekly refresh of the release-truth document landed — the `docs: refresh weekly current-state override` commit, the same one that lands every week, 78 lines changed in the current-state file and 4 in the README. It was an accurate document. That is the part I cannot stop thinking about. Every fact in it was true. It correctly reported that the drift was closed, and it correctly reported that `main` was green, and it wrote both in the same sentence in the "Active blockers" section, which is a section whose entire job is to describe what is *not* finished.

The contract caught it. `tests/evidence_packets/release_truth_contract.py` has a check for contradictions between the recorded release posture and anything else the document claims about readiness, and it failed on both workflows within a minute:

`AssertionError: release-posture-contradiction: the document states 'main` is green', which contradicts the recorded release HOLD`

I went and read why. The contract has a list of nouns that turn a phrase into an artifact rather than the thing itself — gate, checklist, build, branch, candidate, image, tag, version — so "the release checklist is release-ready" stays a narrow, truthful claim about an artifact. And then it has a list of subjects that denote the product itself, and `` `main` `` is on that list, guarded so that "the main documentation is release-ready" does not accidentally trip it. Then a list of readiness verbs, and `green` is one of them. So the sentence "the drift is closed at this tip and `main` is green" was parsed, correctly, as: the product is green. Which contradicts the recorded `HOLD` two paragraphs earlier.

Ten minutes later, one line changed. Not "main is green" — "the tip's `Guardian CI` run is green". The subject became a pipeline instead of the product, and the contradiction evaporated. Both workflows went green at 10:22:13.

I want to be careful here, because it would be easy to read this as "the doc got softened to make a test pass," and it did not. The tip's `Guardian CI` run really was green. The replacement sentence is *more* specific than the original and equally true. What it dropped is the implication that a green pipeline implies a green release — which was never true and which the document contradicted itself about. The claim got narrower because the narrower claim was the correct one. That is the whole difference between weakening something and fixing it, and it is worth having an executable test that can tell the two apart.

There is a pattern there that I think generalizes past today, and it is the same pattern running through the rest of the day from the opposite direction. Every substantive change on the feature refs today was a decision to let the system say less than it could. The chunk service stages oversized files in 8 MiB parts, and its docstring is one line — *"Bounded private transport parts; only existing stage_files admits logical files"* — and the protocol contract says what its four new error tokens do not mean: *"They do not create a new import status, enqueue a worker, authorize another account, or establish archive completeness."* The PDF repair service is 848 lines of owner-authorized repair of exactly one immutable retained PDF, and its five error tokens *"confer no account authority, create no job status and do not relax generic zero-write retry."* The inspector projects fixed metadata and ordered text leaves, and its module comment enumerates what will never escape: no raw body, no envelope, no reasoning field, no tool schema, no response-format object — and oversized captures keep their byte count and omission reasons instead of shipping a truncated substitute.

And the two documents at the end of the day are the purest version of the same instinct. The recall-authority proposal wants to let Guardian answer a question from imported history. It opens with *"Human review of this proposal grants no runtime authority"* and it defers everything that is not the narrowest possible slice. Inside it, a dated report says the original export job was still in receiving with 5,431 of 7,506 files staged and zero conversations processed — so the proposal assumes it has no recallable evidence to work with yet. The Lens preflight is equally blunt: it names the attribution gap (*"`ChatCompletionAttempt` has no Lens invocation/provenance fields"*), and it insists that the voice panel must fail truthfully rather than silently substitute the first voice in a 41-entry catalog. These are documents that would be easy to write as aspirations. They are written as constraints.

Two branches independently produced byte-identical frontend changes — `git diff` between them across `api.ts` and the preflight test file is empty — and one of those branches is cut from a base nine days old that predates both mainline import fixes, including the one that stopped the import service deleting recoverable bytes. The work gets more correct, and the distance to the last qualification receipt gets larger, and both of those things are true at the same time and neither one cancels the other.

So: the build went green because somebody finally computed the number where the thing lives, and then went red because a document said a true thing that implied a false thing, and then went green again because the sentence was narrowed to what was actually known. Three states in one day, and the third one is the only one I would want to keep. A repository that can tell the difference between "the pipeline is green" and "the release is green" — and that enforces the difference with a test — is a repository whose claims I can build on without re-verifying them by hand.
