# Dev Log - 2026-11-01

## Summary

This was an evidence-integrity day, with the heavier code landing on feature refs rather than on `main`. The technical character was making the system's statements about its own state checkable against the repository's history instead of against whatever happened to be in a working tree: the qualification registry stopped being a hand-maintained document that asserted it had been generated, the knowledge-graph corpus stopped hashing bytes from whatever tree the validator happened to run in, and a first-class authorization contract for historical recall was written before the code that will enforce it.

Two larger decisions also hardened today. The dedicated Documents and Gallery surfaces were moved from an open question to a recorded full-retirement decision with explicit phase boundaries and an ownership limit on what retirement is allowed to touch. And the OpenConnector v1.9.4 integration plan was written, checked against upstream source directly, and corrected where reading the source contradicted the plan's assumptions.

None of this moves the release posture. The gate is still `HOLD`, and the qualification registry — for the first time generated rather than asserted — says so in its own blockers.

## What I completed

### Qualification registry: from asserted to generated (mainline)

- `docs/qualification/registry.json` asserted `"generated_from_repository": true`, and nothing in the repository generated or validated it. The registry was hand-maintained, so its freshness was a claim rather than a computation, and its evidence links were never checked against the filesystem.
- Added the missing pipeline. `scripts/qualification/generate_registry.py` projects rubrics and run receipts into `registry.json`, and its `--check` fails when the committed registry has drifted from the evidence it claims to summarize. `scripts/qualification/validate_registry.py` enforces the schema plus the invariants the qualification README states but the schema cannot express: cited rubrics and receipts exist and agree, evidence paths resolve, a `PASS` carries both a tested commit and evidence, and the registry projects exactly the surfaces the rubrics declare. `scripts/qualification/lib/freshness.py` computes freshness from repository history — a run is current when nothing in its rubric's `surface_paths` changed between the tested commit and the tip. A new `qualification-contracts` workflow runs the tests, the drift check, and the validator.
- Added the supported-Compose rubric and a run receipt transcribed from the 2026-09-22 current-tip supported-Compose qualification, plus a rubrics README. The registry continues to report `HOLD` for both surfaces it tracks: onboarding-and-people, which has no run receipt at all, and supported-compose.
- Fixed a defect the new machinery exposed immediately. The first CI run of the drift check reported "1 surface path changed" where the local run reported 116. The cause was the tested commit `5da79431fa059b7da80688380550cf29d4854b18` — the revision the 2026-09-22 qualification evaluated — which was never merged to `main`. It exists in some local clones as a dangling object and is absent from others, so `git diff` against it succeeded locally and failed in CI. The verdict was a function of which objects happened to be in the local object store, which made the check disagree between a developer and CI. Ancestry is now tested with `git merge-base --is-ancestor`, which answers identically in every checkout: exit 0 for an ancestor, non-zero for both a known non-ancestor and an unresolvable revision. A run whose tested commit sits outside the tip's lineage is now reported as `tested_commit_not_in_tip_lineage` and is not current, because it cannot be shown to describe the code the tip contains. The blocker text no longer claims surface paths changed when the real cause was an unresolvable revision, and a missing comparison is still reported as not current rather than silently treated as fresh.

### Knowledge-graph corpus bound to a revision (mainline)

- The document lifecycle graph records, per canonical document, a `content_hash` and a `freshness.verified_commit`. The validator compared the hash against `source_path.read_bytes()` — the working tree — while the revision fields were checked separately for ancestry. The two halves could therefore disagree, and did. Four of the ten canonical nodes carried a hash that matched no revision at all. For `current-state`, the node declared `verified_commit: fe6d2222f` (2026-09-11) while recording the hash of bytes that never existed at that revision. The hash had been refreshed by hand against whatever was in a working tree; the declared revision never moved with it. A reader trusting `verified_commit` would have concluded the document had been reviewed against a revision where it had not.
- The corpus is now revision-bound. Canonical source bytes are read from the Git object database (`git cat-file blob <revision>:<path>`) rather than from the working tree, and a node's `content_hash` is compared against the bytes at that node's own `verified_commit`. The verdict is a function of the repository's history alone, which is what let the corpus drift silently under multi-worktree development. A working-tree edit to a governed document no longer produces a spurious mismatch.
- `rehash` rebinds nodes to a revision, writing `content_hash` and `freshness.verified_commit` together so they cannot drift apart again. Rebinding is mechanical: it records which bytes a node describes and does not assert that a human re-reviewed the document. `freshness.state` is changed only by human review or an approved proof workflow, and a node already marked stale stays stale until a reviewer says otherwise. The ten canonical nodes were rebound and are internally self-consistent, including the `current-state` and `kb-entrypoint` nodes.
- Closed the drift gate itself. The Architecture Contracts workflow now triggers on the corpus and DLG tooling paths — `docs/knowledge-graph/**`, `schemas/knowledge/**`, `scripts/knowledge_graph/**` — which were absent from its filter. That omission is precisely why the corpus could drift: a change to a canonical document or to the DLG tooling did not run the tests that would have noticed. A governed document changing after a node's verified commit now fails the corpus test unless the node already declares itself stale, and staleness is reported as a finding rather than an error, which is the right shape for a report and the wrong shape for a gate.
- Fixed a script-resolution defect found by running the rebind tool as a script rather than importing it, and rebound the canonical nodes to the resulting revision.

### Request-bound history recall authorization (feature ref `feat/auto-20261030-3c15309a`)

- Extended ADR-084 to define historical recall intent authorization: a trusted intent source, a recognition method with stated limits, the authorization decision itself, grant binding and lifetime, scope enforcement, denial behavior, imported-history exclusions, and an explicit no-memory-promotion rule. The contract is scoped to recall permission only and leaves ADR-005, ADR-081, and existing thread and message read authority as independent requirements.
- Implemented the enforcement. `guardian/core/account_history_recall.py` grew by roughly 1,500 lines, with the completion service and the model-visible tool exposure updated to route through it. The work is a behavior change: recall is now bound to the request and its authorized intent rather than to the presence of history. The surface carries a deliberate read-only envelope, an advertisement gate, and an execution gate, and ordinary chat advertisement stays inactive.
- Wrote a new clarification to ADR-016 defining authoritative chat message origin, on the principle that origin, ownership, authorship, and placement are different facts and none substitutes for another. Positive native proof is a message-associated origin assertion assigned by the trusted canonical backend at the creation of that native interaction, atomically with the message insert, using the existing `ChatMessage.extra_meta` object rather than a new subsystem. The clarification authorizes no runtime activation, migration, backfill, importer rewrite, restore change, or historical relabeling, and it is explicitly a target contract rather than a claim that writers or readers already enforce it.

The deciding factor was that the Dashboard is itself slated to become a Feed and already carries projections that Library embeds — keeping three documents projections alive would preserve exactly the ambiguity the pass was meant to close.

The `/documents` and `/gallery` routes stay live and addressable by URL, so browser-local gallery content remains reachable, and the navigation specs now reach the retired destinations by URL while asserting their absence from the top navigation.

### OpenConnector v1.9.4 integration plan (feature ref `mcode/31b4bff7-5ff0-43f7-9879-7e88f1405a8e`)

- Wrote the integration plan, then adopted an explicit pin-but-track upstream maintenance commitment — pin, monitor, evaluate, remediate, stop — with a licensing boundary and an explicit exclusion of any dedicated monitoring subsystem. The plan also distinguishes containment from authorization, keeps Gate A inside its scope so a plan does not quietly become an implementation commitment, and sequences the ADR-094 amendment after Gate A rather than before it.
- Corrected six preparation defects found by reading upstream v1.9.4 source and the Docker Compose documentation directly. One grant assumption did not survive that reading: the plan's trial credential was broader in effect than the plan assumed it would be, so it now follows a phased lifecycle in which the initial broad grant is revoked before any credential-bearing connection exists. The runtime authentication bootstrap needed an explicit ordered sequence ending in proof that an unauthenticated request is rejected. `env_file` and interpolation are different mechanisms with different sources, so the deployment uses `env_file` alone behind a fail-closed preflight that reports key names only. `GET`-only is a Command Bus classification rather than a read-only guarantee, so Gate B now requires a reviewed, server-controlled read-only allowlist. Proof classifications were split so a local-only executor test cannot be reported as a live unauthenticated call, and the NOTICE framing was separated from what the license legally requires.
- Verified the Compose execution policy by rendering the exact block from the plan with `docker compose config` against a dummy secret file, with no container started, and asserting the resolved environment. All twelve assertions passed — blocked proxies, empty allowed proxies, a narrow non-empty allowed-action set, both secret keys present, the runtime-token key absent, private networking disabled, a digest-pinned image, and no published ports. Two fail-closed behaviors were confirmed: a missing `env_file` refuses to start, and an empty allowed-action list still renders successfully, which is why the preflight checks it.
- Tightened the gate-A preflight to reject the runtime-token key regardless of value, to require the allowed-action list to equal exactly the approved trial actions with no wildcards, and to block provider triggers at the deployment layer, since triggers are evaluated by an independent policy from actions and proxies and the token-level defense does not reach them. The bootstrap rejection was moved to a group that runs before any credential exists and is re-run after every handoff, after restart, and after the last user token is deleted.

## Important outcome

The system's claims about itself stopped being hand-maintained. Before this day, the qualification registry declared that it had been generated from the repository when nothing generated it, and the knowledge-graph corpus carried content hashes refreshed by hand against whatever tree was convenient while the declared revision stayed where it was. Both of those are the same failure in different clothing: a report whose freshness is asserted rather than computed. Now the registry is a projection of rubrics and run receipts with a validator, and the corpus's hashes are compared against bytes read from the Git object database at the very revision each node names. The verdict is a function of the repository's history, which means it cannot depend on which worktree, which branch, or which dirty state the tool ran from. That is the property that matters under multi-worktree development, and it is now a property the tooling has rather than a habit the team has to maintain.

The second shift is that the largest remaining surfaces are moving contract-first. Historical recall now has an authorization contract that says what a grant is, how long it lives, what it may reach, and what it may never promote into memory, and the enforcement code is being written against that contract rather than inventing semantics as it goes. The message-origin clarification makes the same move for a harder question — what counts as native evidence — and it is explicit that it describes a target, not a shipped guarantee. And the Documents and Gallery retirement now has a recorded decision, a phase sequence with an explicit enabling step, and an ownership limit on what the phrase is allowed to mean. The pattern is consistent: decide what is true, write it down, then let the code be held to it.

# Dev Log - 2026-11-01

The day had a shape that only became clear in the evening. Most of the code did not land on `main`. What landed on `main` was mostly machinery for checking whether anything was true — and the code that did land was sitting on feature branches, waiting for a decision or a review. That is worth naming before anything else, because the temptation in a daily log is to describe the day's work as if all of it shipped, and today, on the most consequential parts, it did not.

Take the qualification registry. It carried a field reading `"generated_from_repository": true`, and nothing in the repository generated it. A file was maintaining itself, and the file said it had been built by something else. The evidence links it cited had never been checked against the filesystem, so the registry could point at paths that did not exist and still read as a record of what had been proven. The work today was to give it a generator, a validator, and a definition of freshness, and then to discover, on the first CI run, that the freshness computation itself was not deterministic: the local machine said one surface had changed, CI said a hundred and sixteen, and the difference turned out to be a git object that existed in one clone and not another. The verdict had depended on what was lying around on disk. Ancestry testing replaced it, and the answer is now the same everywhere: this revision is not in the tip's lineage, so this run cannot be shown to describe the code the tip contains. That is a worse-sounding sentence than the one it replaced, and it is the correct one.

The knowledge-graph corpus had the same disease in a more dangerous form. Each canonical node carried a content hash and a declared revision, and the two were checked separately — the hash against the working tree, the revision for ancestry — so they could disagree. And they did: four of the ten nodes carried a hash that matched no revision at all. The `current-state` node claimed to have been verified against a revision from September while recording the hash of bytes that never existed there, because someone had refreshed the hash by hand against whatever tree was open and the revision field had never moved with it. A reader who trusted that field would have believed a document had been reviewed against a commit where it had not been. Now the bytes come out of the git object database at the revision the node names, and a node that says which bytes it means has to mean them. The tenth canonical node is now internally consistent. It is not re-reviewed, and the distinction is deliberate: rebinding is mechanical, and only a human can move a node out of stale.

The larger surfaces moved differently. Historical recall — the ability to reach back into what an account actually said — got a contract before it got its enforcement: a trusted intent source, a recognition method with honest limits, a grant bound to a request and to a lifetime, a scope that cannot widen, and an explicit refusal to let a recall become a memory. The implementation is large and it is sitting on a branch. Meanwhile a second clarification went into ADR-016 on the question of what counts as native evidence — because a message's owner, its author, its thread, its current project, and the system it came from are five different facts, and a record that was copied in from elsewhere cannot be laundered into native creation by being stored well. The contract states this as a target. It says plainly that it authorizes no migration, no backfill, no relabeling, and that the writers do not yet enforce it. There is something quietly reassuring in a document that describes its own enforcement gap in the first paragraph.

And then the product decision: the dedicated Documents and Gallery destinations are to be retired — not the resource families, not the archives, not the ownership and provenance systems, but the top-level destinations and, eventually, the page shells, with the routes staying reachable by URL for now. The Dashboard's redundancy was the deciding argument, since it is on its way to becoming a Feed and already duplicates projections Library carries. The plan earned the decision by checking its own premises first, and the checking changed the plan twice: Gallery content turns out not to be fully represented in Library, `cfy.gallery` is browser-scoped rather than account-scoped, and the Library filter that would absorb all of this is not addressable yet. That last one is Phase 2, and it is the enabler. So the first code change of the plan removes two navigation pills and nothing else — deliberately small, with the routes still live, and the specs rewritten to reach the retired places by URL and assert they are gone from the top nav. The nav is thinner; the honest work is in the phases after it.

The OpenConnector plan took the other shape of the day: read the source, distrust the summary, correct the plan. Several of its assumptions about upstream v1.9.4 did not survive reading the upstream source directly, and the plan was wrong in ways that would have produced a broken integration rather than a failed one — the trial credential in particular was broader in effect than the plan assumed. The deployment's execution policy was verified for real: the exact compose block rendered against a dummy secret file, no container started, twelve assertions on the resolved environment, two fail-closed behaviors confirmed. Some of the upstream findings in that review are security issues in a supported release and are under a private disclosure hold, so this public log names the work and omits the mechanisms. That is the correct shape for a log that anyone can read.

The honest accounting is that the release did not move. The gate is still `HOLD`. The registry — now that it computes instead of asserting — reports `HOLD` for both surfaces it tracks, including one whose evidence lives in a revision the current tip cannot claim. The knowledge-graph corpus got tighter, not truer; the state document it describes is still the 2026-10-31 refresh, and no node was re-reviewed. The recall enforcement is unreviewed on a branch. And nothing here is a live runtime proof; there is no dated receipt for this day at all.

What did change is the system's ability to be caught lying to itself. A registry that generates itself cannot quietly claim freshness it does not have. A corpus hashed at its own revision cannot describe a commit it never read. A drift gate that fires on the paths that matter can notice when the corpus stops matching the documents. These are not capabilities anyone would put on a feature list, and they are the reason the rest of the list can be believed when it is eventually checked. The day added very little that a user would notice, and a great deal that will keep a future claim from being mistaken for a current fact.
