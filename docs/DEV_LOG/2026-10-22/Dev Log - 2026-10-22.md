## What I completed

### Delegated write-scope contract

- Replaced the empty repository-scope entry with the explicit `.` repository-root token understood by the worker, and rejected scopes that contain no usable entry. The grant still requires a resolved repository root and an explicit write authorization.
- This makes the scope passed across the Guardian/worker boundary interpretable instead of relying on an empty value with ambiguous meaning.

### Account-owned GitHub snapshots

- Added bounded issue and pull-request snapshots on the existing `raw_documents` persistence surface. Ownership is resolved through the canonical account identity and account-owned connector configuration within the database transaction; a caller-supplied connector ID alone is not authority.
- Snapshot identity retains the source repository, and input fields, batch size, and payload size are bounded. The module does not fetch from GitHub, read credentials, promote snapshots to canonical memory, or automatically retrieve them.
- Added database and route tests for ownership and persistence behavior, plus architecture documentation for the storage boundary.

### Guardian-governed reasoning effort

- Added a versioned execution-binding schema that can carry the reasoning effort Guardian authorized. For the specifically validated DeepSeek V4 Flash lane, unsupported choices fail closed instead of being silently substituted; the worker forwards the bound value rather than choosing one itself.
- Version 1 bindings remain valid and continue to leave effort selection to the harness. The compatibility list is deliberately narrow and is not a general model-capability registry.

## Important outcome

Delegated execution now has more explicit inputs at two sensitive boundaries: repository write scope and reasoning effort. These values can be tied to Guardian's authorization rather than inferred from blank scope data, caller task fields, or worker-side defaults.

GitHub snapshots also gained an account and source-provenance boundary before persistence. That makes the storage path more resistant to cross-account selection and repository relabeling, without claiming a live connector or retrieval capability.

# Dev Log - 2026-10-22

Today was a contract-hardening day, not a release milestone. The work came through two feature refs and concentrated on places where one component hands authority or persisted data to another. The useful change was not a new user-facing surface so much as less room for those boundaries to be interpreted differently.

The first correction was small but consequential: an empty path entry was being used where the worker expects a repository-root scope token. Guardian now emits the explicit `.` representation and refuses a write posture whose scope is empty in substance. The grant still depends on a resolved repository root and explicit write permission, so the token describes an already-authorized boundary rather than creating one.

The GitHub snapshot work applies the same discipline to stored source material. A snapshot is attached to the account-owned connector through a transactionally resolved ownership chain, and its external identity preserves which repository it came from. The persisted fields and payload are bounded. Just as important, this layer does not fetch remotely, read credentials, or turn snapshots into canonical memory or automatic retrieval. It establishes a storage boundary, not a complete connector capability.

The final change carries a Guardian-selected reasoning effort through a versioned execution binding. The supported compatibility rule is intentionally limited to the validated DeepSeek V4 Flash lane; an unsupported request fails rather than being downgraded. Older bindings retain their prior behavior, and the worker does not invent a choice. This reduces hidden policy drift between authorization and execution, while leaving unlisted model lanes outside the new guarantee.
