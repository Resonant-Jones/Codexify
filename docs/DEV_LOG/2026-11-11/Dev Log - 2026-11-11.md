## Important outcome

The day's structural shift was in the difference between a check that is *correct* and a check that is *correct today*. The eight-gate self-test had been passing for the wrong reason since it shipped: it looked like a guard, but what it actually encoded was a memory of one particular revision. When the migration that advanced the head to `ab71d5ce9604` landed on 2026-11-09, it began failing against a harness that was working correctly — and a check that cries wolf at every tip is a check nobody can act on. The replacement is not more validation; it is a change in where the expected value comes from. It now comes from the same source the thing under test reads, computed by a different method, so the two can disagree.

The same discipline showed up in the release-truth document, pointed the other way. That document had carried a line asserting a green CI run at the tip. When the tip's own run came back red, the honest move was not to re-run until something green appeared but to record the red result, name the failing assertion, mark the flake theory as a working theory, and add an explicit prohibition against reading the red run as either a product defect or a clean tree. The document now also says plainly that a green run, a `PASS` gate and a host-capacity `GO` are not runtime qualification.

Both changes are about the same thing: an assertion that cannot fail on its own is decoration. The mutation proof exists to make that claim checkable rather than rhetorical — it proves the head check can still fail, that it follows a superseding revision, that it fails closed on a two-head graph, and that it agrees with Alembic. That is a larger commitment than adding a second assertion, and it is the part of the day that will still be true next month.

# Dev Log - 2026-11-11

It was a day of two honest documents, and one of them turned out to be about the release gate.

Start with the red one. The weekly refresh of `docs/architecture/00-current-state.md` is a routine commit — the file gets rewritten every few days, its "Last updated" date advances, its priorities get renumbered. It is also the document that the whole repository's release reasoning points at. So when it was refreshed on the eleventh, the change that mattered was not in the priorities section. It was in the section that records what is true about the tip, where a line had been sitting since an earlier week asserting that the CI run at the tip was green. "Proven in live runtime at this tip" was the phrase. That line was removed, and in its place went the sentence that the tip's own run concluded `failure`: backend green, alembic green, migration contract green, Frontend Quality red.

That is a strange thing for a project to state about itself, and it is worth noticing what the document did next rather than just what it stopped saying. It named the failing file. It named the failing case — a frontend timing-sensitive assertion in `GuardianChat.turn-lock-lifecycle.test.tsx`, the one that expects a cancel POST and never receives it. It observed that the `frontend/` tree was byte-identical to the previous green run's. It noted that this same file had failed non-deterministically on `main` before, with no `frontend/` change. And then it labelled its own conclusion precisely: a working theory, load or timing dependent, not a regression — and unproven, because no one had re-run that particular run.

Then, because a red run invites two opposite over-readings, it wrote down both ways not to read it. Do not read it as a product defect. Do not read it as a clean tree. And it added a broader prohibition that would outlive the incident: do not read a green CI run, a `PASS` gate, or a host-capacity `GO` as runtime qualification. Those prove a claim is checkable. They do not prove the runtime behaves.

The second honest document was the eight-gate self-check, and its story is stranger because the check had been *failing*, loudly, for two days — and the failure was the symptom of a bug in the check.

The self-check's job is to assert that the evidence harness computes the checkout's single Alembic head from its own source. That is a real assertion about a real property, and it is worth making. But it compared the harness's answer against a pinned literal: the revision that was the head on the day the harness shipped, 135 revisions ago. So the moment anyone added a migration, the check reported 53 of 54, every time, on every tip whose head had moved. The harness was reading the head correctly. The check was holding a photograph of a revision that no longer existed and grading the present against it.

There are two ways to repair a check like that, and the interesting one is the way that was chosen. You can re-pin the literal to the current head — which is what the priority list had been asking for, and which would have worked perfectly until the next migration, at which point the same false failure would return wearing a new revision number. Or you can make the check compute its own expectation. The second one is what landed: each revision file's `revision` and `down_revision` declarations are read with `ast`, and the head is the revision no other revision descends from. No Alembic, no `alembic.ini`, and — this is the part that matters — no dependency on the code being judged.

That last property is the whole argument, and the commit message makes it in one clean sentence: taking the harness's own answer as the expected value would never go stale, but it would also agree with a harness that computed the wrong head, and the check would pass. Two independent computations can disagree. One cannot. It is the difference between a mirror and a second opinion, and a mirror cannot tell you it is wrong.

And then the part that could have been skipped. A check that has been rewritten to compute its own expectation deserves a check of its own, and the day shipped one: a mutation harness that makes four deliberate breakages and asserts the check catches each. Mutate the harness to report a stale head — the self-check must fail and exit non-zero. Add a revision that supersedes the current head — the expected head must move with it, which the pinned literal never could. Give the source two heads — the computation must report no head rather than picking one, failing closed rather than guessing. And compare the independent computation against Alembic's own revision map — they must name the same head and the same count. Each mutation starts from the pristine file, so one cannot mask another, and every file is restored byte-for-byte whether the mutation was caught or not.

I checked this myself, at the fetched tip rather than from the commit message, because it was cheap to check and the whole point of the day was about claims that are cheap to check. The self-check reports 54 of 54. The mutation harness reports 12 of 12, ending with `PASS: every mutation behaved as the check claims`. One honest note from doing it: run under a Python without Alembic installed, the self-check does not fail gracefully — it reports the head check as failed and then trips over a missing key, because the harness side genuinely needs Alembic to compute its own answer. The fix is a correct one; the failure mode is just not a graceful one. Worth knowing before someone runs it in the wrong environment and concludes the fix is broken.
