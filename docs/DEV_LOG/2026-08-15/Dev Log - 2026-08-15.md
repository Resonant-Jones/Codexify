# Dev Log - 2026-08-15

## Summary

This was an execution-boundary and release-governance day. Mainline absorbed the Campaign Engine live-role execution contract and then canonized Codexify’s Beta support boundary in ADR-069, while also landing the canonical conversation-origin system and the Anthropic account-import adapter.

The central shift was not a broad feature promotion. It was a sharper distinction between what the product may support, what the code can do, what has been proven at runtime, and what remains outside the release promise.

- Kept evidence maturity, support posture, runtime participation, integration state, and strategic posture orthogonal.

- Established the canonical conversation-origin system so imported and native conversation records can retain their origin semantics.
- Added the Anthropic export adapter to the account importer, extending import coverage without weakening owner scope or continuity boundaries.

## Important outcome

Codexify now has a canonical language for saying “supported,” “internal,” “conditional,” “experimental,” or “out of Beta” without confusing those classes with runtime proof. The release boundary became a real governance surface rather than a loose summary of whatever code happened to exist.

The import and execution work benefits from the same discipline. Conversation origin is explicit, and live-role execution has an authorization and receipt boundary. Both changes make it harder for capability, access, or acceptance to masquerade as ownership or completion.

# Narrative Log - 2026-08-15

This was a day when execution and release language were forced to meet the same standard. The Campaign Engine live-role contract landed with explicit authorization and receipt boundaries. That does not mean a live run has been completed; it means the system now has a more precise shape for one, and a clearer rule for what evidence would count.

The larger change was ADR-069. Codexify now has a canonical Beta boundary with five human-facing release classes and an authority hierarchy for reconciling documentation, posture assertions, supported configuration, and proof. That matters because “the code exists” and “the product supports this” are different statements, and so are “the runtime ran once” and “this path is release-supported.”

The conversation-origin system and Anthropic importer extended the continuity surface under the same discipline. Imported records need to retain where they came from, and added adapter coverage must not quietly become a new owner or persistence authority.

The deeper shift was toward explicit classification. The system stopped asking one overloaded question—“is this supported?”—and started separating support, runtime participation, evidence maturity, and strategic posture. That gives the project room to move without having to rewrite its own limits every time a new seam appears.

The next move is to let those boundaries constrain actual proof: one authorized execution attempt, one origin-aware continuity path, and one supported-profile reconciliation at a time.
