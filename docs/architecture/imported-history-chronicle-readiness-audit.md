# Imported-History Migration Chronicle Readiness Audit

Date: 2026-10-09. Lane: architecture-impact. Status: discovery intake; implementation parked. Evidence: static source inspection and documentation validation only.

## Finding

A read-only Migration Chronicle preview can plausibly reuse canonical imported threads and messages without changing persistence or chat-retrieval authorization. That is a design conclusion, not proof of an implemented preview. The smallest reusable seam is an account-bound, explicitly Project-bounded read over canonical conversation records, upstream of any summarizer. It does not require embeddings, a provider call, new memory records, or continuity persistence.

The immediate prerequisite is missing: a bounded imported-history evidence reader that jointly enforces account ownership, Project ownership, explicit source selection, exclusions, provenance completeness, and honest partial/error reporting. Existing individual readers do not establish that combined boundary. A production preview and transcript-to-orientation extraction are also unproven/missing. The recommendation in §8 closes only that reader prerequisite.

[Current state](00-current-state.md), dated October 9, retains supported-Compose `HOLD` and explicitly does not establish a complete natural import-to-recall path. That recall qualification remains open; it is not evidence that canonical history cannot be read. Conversely, a successful direct history preview would not close the recall gate.

Two provenance limits must stay visible:

1. `anthropic_export_adapter._normalize_conversation_record` attaches Anthropic format/path metadata, but `chatgpt_migration.ingest_claude_export` supplies an empty `import_grouping_metadata` to the writer. Adapter tagging therefore does **not** establish durable Anthropic conversation source-path preservation. Canonical origin and message/source IDs remain available; archive-path claims must be omitted or marked unavailable. The separate document path has its own provenance.
2. `_normalize_mainline_messages` and `_normalize_claude_messages` calculate `source_created_at_inferred`, but `_write_canonical_messages` does not include that flag in canonical `temporal_meta`; it does include it in embedding metadata. OpenAI can also fall back to a conversation timestamp without setting the flag. A Chronicle cannot treat every persisted `source_created_at` as an exact authored message time. It must inspect available raw timestamps or report unknown/fallback basis, never use vector metadata as canonical temporal authority.

The writer does not attach an import-job ID to every conversation in this path. `OpenAIAccountImportService.record_conversation_batch` records job checkpoints, while message metadata carries source IDs. A selected job's counters alone cannot define an exact conversation corpus; a future reader must resolve and verify membership or leave job-level linkage unavailable. No reconstruction by title, filename, or nearest timestamp is authorized.

## 4. Existing memory and continuity paths

`backend/rag/personal_fact_extraction.py::extract_personal_fact_candidates` and `extract_personal_fact_candidates_third_person` use rule-based extraction. `chatgpt_migration._classify_import_candidates` invokes the Personal Facts guardrail classifier; discarded candidates are removed, and quarantine/review metadata travels with retained candidates. `persist_personal_fact_candidates` writes the **legacy** `personal_facts` / evidence path with candidate status, source references, excerpts, and duplicate checks; it skips existing non-candidate facts. This is not the amended UMS candidate implementation and must not be reused to create Chronicle facts.

`import_openai_export_conversations` exposes `disable_personal_facts` and `messages_only`, but both default false. The background worker passes embedding deferral without either fact-disable flag. Therefore “read existing imported history” and “rerun the importer to obtain a preview” are materially different operations. The latter may write candidates and is outside the proposed preview. `persist_personal_fact_candidates` also uses its `CHATGPT_IMPORT_SOURCE` evidence constant through the shared path; candidate evidence alone must not be used to infer Anthropic versus OpenAI origin without canonical source lineage.

The current human read/review seams are:

- `guardian/services/memory_vault_read.py::MemoryVaultReadService.list_items/get_item` projects account-filtered `memory_records`, persona links, provenance, and compatibility sources without minting synthetic canonical identities. `VaultListFilter` permits Project/source/species filters. `_project_canonical_row` derives posture from the currently implemented row fields; it does not prove support for the amended candidate fields.
- `guardian/routes/memory_vault.py::_resolve_vault_account` requires `RequestUserScope.account_id`; `get_memory_vault_read_service`, `list_vault_items`, and canonical/compatibility detail handlers expose that reader. `guardian/guardian_api.py` registers it through `_include_router` under `CODEXIFY_ENABLE_MEMORY_VAULT_ROUTES`, default enabled but not a core release surface. Registration is not deployed proof.
- `guardian/routes/personal_facts.py::list_personal_facts`, `get_personal_fact`, and `list_fact_evidence` expose legacy fact inspection; `approve_candidate` and `reject_candidate` are separate account-bound transitions with guardrail checks. Chronicle does not call those mutations or label its own output verified.

[ADR-084](adr/084-unified-account-owned-memory-store.md), “Personal Facts remain specialized,” and [UMS contract §3.4](unified-memory-store-contract.md#34-personal-facts-authority) explicitly distinguish the amended target: one UMS `candidate_unreviewed_fact` owns pre-promotion review/quarantine; promoted `personal_facts` owns fact review/activation. The contract explicitly states that the current schema/compatibility readers do not implement the amendment. Its raw-key, replay, evidence, promotion, and export gates are not satisfied by the legacy importer. The older [Vault contract](memory-vault-contract.md), “Personal Facts posture,” must be read with that later amendment; it does not authorize a second candidate authority. This is an explicitly documented transition, not an unresolved choice between co-authorities.

`guardian/continuity/compiler.py::compile_reality_state` is a deterministic contract harness over explicit structured `ContextPacket` inputs. It does not read transcripts, infer facts, summarize text, authorize access, call providers, or persist output. Its open-loop fields are assembled from supplied packet payloads, not extracted from imported conversations.

There is bounded continuity infrastructure beyond that harness: `guardian/continuity/persistence.py::ContinuityPersistenceAdapter` and `guardian/routes/continuity_operator.py::create_reality_stamp/read_reality_state`. The latter uses `require_operator_auth`; its mount in `guardian/guardian_api.py` is default-disabled through `CODEXIFY_ENABLE_CONTINUITY_OPERATOR_ROUTES`. Operator capability is not an account user's history grant. Neither seam is a safe substitute for a Chronicle account reader or proof of Project Pulse. No continuity writes are needed for an ephemeral preview.

## 6. Proposed preview boundary and output

This section is a proposal for later review, not a new runtime contract or token registry. First restrict a preview to one explicitly selected, canonically account-owned Project, across selected imported threads within that Project. Broader account-wide or cross-Project synthesis requires its own explicit scope and exclusion proof; no default “all accessible history.” Native messages appended to an imported-origin thread must be distinguished by message-level import provenance and excluded from an imported-history-only selection. Thread origin alone does not prove every message was imported.

The client requests inspection; Guardian resolves identity and enforces source scope; PostgreSQL supplies canonical evidence; an eventual local summarizer may only interpret the already-authorized bundle; the client renders an inert preview. Archive text and model output are untrusted across the content-to-authority boundary. Infrastructure operators, external providers, source accounts, and Redis task IDs supply no account-history authority. The first slice has no model node at all.

| Proposed output | Required contents and source/access basis |
| --- | --- |
| Scope and coverage | Account-bound request reference, explicit Project/thread selection, canonical origins, read time, inspected counts, bounds/cutoffs, exclusions by content-free reason, omitted/failed sources, and whether coverage is partial. Source: §5 thread/message readers plus validated policy; never claim complete history from a capped page. |
| Candidate facts | Bounded user-stated propositions with quotes and source links; distinguish an ephemeral observation from a persisted UMS candidate or verified fact. Existing fact review context, if later shown, keeps its original identity/status through the §4 reader. Sensitive/inferred traits are suppressed absent their separate consent boundary; no auto-approval. |
| Interaction preferences | Distinguish explicitly quoted historical instructions from inferred stylistic preferences. Show source role/content type and source system. Historical preference is not current user intent; no adoption into Lens, Persona, system prompt, or account settings. Source access: §3 retained messages only until missing families are separately supported. |
| Ongoing projects | Historical project mentions and last observed activity; canonical Codexify Project ID/name remains separate from a source-provider Project ID or inferred work theme. “Ongoing” must be tentative unless current user confirmation exists. Text access: §5; no source-Project mapping invented from titles/GPT IDs. |
| Historical milestones | Event wording, supporting message refs, source dates and their known/fallback/unknown basis. Keep incompatible dates/claims visible. Use canonical content and preserved raw timestamp evidence, with §2 limitations. |
| Open loops | Quoted unresolved requests/commitments or explicitly labeled derived interpretations, last evidence date, and “resolution not found in inspected scope” rather than a claim of still-open current state. No task enqueue or completion mutation. Extraction remains missing. |
| Per-item provenance | Canonical thread/message IDs, Project ID, `origin_system`, original source thread/message IDs, role/raw role/content type, import profile, source path/job/fingerprint only when verifiably available, and an account-authorized navigation reference. A source path is evidence text, never an executable file/link instruction. |
| Freshness and confidence | Separate source event time, import time, preview read/generation time, source revision/hash where available, and derivation version. Human-readable labels: direct source statement, explicit historical instruction, derived interpretation, conflicting evidence, insufficient evidence. These proposed presentation labels are not approval states or registered protocol tokens. Avoid invented probability scores; source-model confidence is not truth. |
| Review boundary | Every derived item is an unapproved preview. User may inspect supporting history and dismiss the ephemeral view. Approval/activation, saved preferences, durable candidates, edits, and retention require separate governed actions; no button or generated text silently performs them. |

Revisions/deletions or changed exclusions invalidate the preview; regenerate on explicit request after reauthorization. No persistent cache, new schema, index, automatic refresh, hidden provider context, or inference-derived identity is proposed. Bounded reads must either use a consistent read strategy or disclose concurrent-change incompleteness. Conflicting assertions remain separately sourced; there is no silent last-write-wins factual merge.

Failure priorities are: wrong account/Project (reject before content), excluded/unknown-policy source (suppress or stop), missing provenance (omit affected claims and report coverage), unavailable storage (explicit failure, not empty success), and stale/contradictory history (label uncertainty, do not assert present truth). These follow ADR-016 exclusions, ADR-081 ownership, and the UMS untrusted-evidence/authority separation, without changing chat retrieval policy.

## 7. Precise blocker and non-blockers

**Blocker to a safe preview implementation:** no identified account-bound imported-history reader composes all §5 requirements and returns content with trustworthy coverage/error semantics. The generic chat reader is useful source infrastructure, but neither it nor the continuity compiler supplies that proof boundary. In particular, single-user optional account filtering, independent Project ownership, exclusions, mixed native/imported messages, and metadata/error handling require an explicit adapter contract and tests before synthesis.

**Additional gap to a full five-family orientation:** transcript extraction and its source-grounding/review behavior are not implemented by `compile_reality_state`. This audit does not admit inference work now.

**Not required for the proposed first slice:** embeddings or Chroma repair, provider context assembly, natural recall qualification, amended candidate persistence, a new Project, continuity packet/state writes, Anthropic memory import, Project Pulse, or durable Chronicle artifacts. Reading existing eligible canonical rows can be implemented independently; that independence grants no release qualification or permission to skip exclusions.

Known source/document differences are recorded rather than repaired: the import runbook's WebUI section describes the legacy single-file lane; the diagnostics document's asset discussion describes its forensic adapter lane; the current worker/service contains broader durable account-import paths. Those historical lane descriptions are not used as current UI support evidence. ADR-015's original future-engine statement does not erase later bounded operator infrastructure, and ADR-084/UMS explicitly labels its candidate amendment as target architecture. No unresolved governing-authority conflict was needed to select this audit boundary.

## 8. Exactly one recommended subsequent implementation slice

**Implement and prove a bounded imported-transcript evidence reader for one authenticated account and one explicitly selected Project.** This is a prerequisite closure candidate, parked until separately admitted and authorized; it is not permission to build Chronicle inference or UI.

Place the read-only composition in a dedicated Guardian service beside the existing read services, reusing canonical `PgDB` storage and existing ownership classification. Before implementation, freeze its small input/output and error contract under architecture-impact review: trusted resolved account, selected Project/thread IDs, explicit imported origins, bounded limits, and a complete applicable exclusion decision. Reject absent/ambiguous policy; do not invent default consent or new persisted governance. No public route, worker, new table, provider, vector retrieval, fact extraction, memory mutation, continuity write, or UI is part of this slice. Proposed serialized values require existing-registry review under ADR-030; this audit registers none.

Output only bounded historical excerpts, original authorship/type, canonical/source references, timestamp basis, and a content-free coverage/error receipt. Check account and Project authority before returning content; use message provenance to omit native additions. No generated fact/preference/project/milestone/open-loop interpretation yet. This supplies the minimum trustworthy input seam for later preview work.

Required proof gate before calling the reader complete:

1. Disposable PostgreSQL fixtures with two accounts, multiple Projects, both imported origins, native-only threads, and native messages appended to imported threads. Same-account/selected-Project imported records are returned; all negative scopes return no content, including single-user-mode requests and forged IDs.
2. Ownership conflict, missing owner, diary/modeling/identity exclusions, explicit thread/Project exclusions, and missing policy fail closed. A human-authorized archive read must not be treated as permission to model excluded material.
3. Bounds, deterministic ordering, duplicate source IDs, missing source dates/IDs, changing rows, and partial imports yield honest coverage. Database/metadata failures cannot become successful empty history. Do not rely on the unimplemented PgDB cursor argument identified in §5.
4. Source refs resolve only under the same account/Project checks. Historical instruction text and adversarial imported content remain literal evidence; they cannot trigger tools, widen reads, alter settings, or approve facts. Test exact role/origin separation and null rather than fabricated archive/job provenance.
5. Assert no canonical or derived writes, fact extraction, embedding enqueue, provider calls, continuity calls, or external access. Compare before/after canonical rows and use a read-only database transaction/role where practical. Report service-level proof separately from any later supported-Compose proof.

Failure at any gate blocks preview integration; it does not authorize importer or ownership repair in the same task. Future inference must separately prove grounded output, sensitive-content boundaries, local-only provider policy, and no ambient activation. Any supported end-to-end claim still requires the separately defined live gate and current-state review.
