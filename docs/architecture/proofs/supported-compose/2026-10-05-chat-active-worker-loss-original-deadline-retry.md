## Durable orphan and fencing

After the original terminal deadline, the existing receipt API reported terminal `task.failed`, reason `durable_terminal_outcome_recorded`, with `CHAT_ACCEPTED_TASK_ORPHANED` reconciled at `2026-10-05T04:35:17.087035+00:00`. PostgreSQL retained the exact attempt/deadline, null completed message and immutable orphan outcome. Matching Redis lock cleanup completed; queue remained empty. The implementation commits durable fencing first and performs separately bounded strict owner/token Redis cleanup; this proof is not a cross-store transaction claim. Raw original events retained created/running evidence without an invented terminal publication.

The repository refused a late assistant for the exact orphan tuple. A rollback-only wrapper ensured unexpected writes could not commit. Three direct PostgreSQL mutation probes—late completion binding, replacement cancellation kind, and clearing orphan outcome—were rejected by the orphan trigger with SQLSTATE 23514. Every probe transaction rolled back; final row/message preservation checks found no probe writes or ghost assistant. This validates persisted fencing and the repository guard, not delivery from a resurrected killed process.

The browser automatically showed “1 earlier response request was closed after the recovery deadline without a recorded completion. Send a new request to try again.” Reload preserved the authored message and orphan notice with no assistant. The notice distinguishes an unresolved lost-task reconciliation from controlled execution timeout.
