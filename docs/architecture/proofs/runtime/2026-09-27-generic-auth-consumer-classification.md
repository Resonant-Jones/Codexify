## Scope, method, and authority

This supersedes this receipt’s earlier HOLD classification at `12899eedc0b6d71a1dd821f26f33cb4533a1cfe0`. ADR-049 §9 and ADR-092 now settle the human-admin/service-key relationship. Their accepted semantics, ADR-039’s operator/user split, current identity/runtime contracts, and live production source govern this static map. No current generic-auth behavior is promoted to accepted architecture. The Continuity PostgreSQL qualification remains the separate prior proof.

An AST sweep of production `guardian/**/*.py` route declarations and direct calls found **364** auth-relevant route registrations: **325** linked to a named primitive or a transitive wrapper and **39** adjacent account-scope/session/admin routes. Fifteen additional issuer, public, and Hosted Room guest registrations were traced manually. The complete route-level table below therefore classifies **379 registrations** (including aliases and disabled/unmounted declarations), not 379 distinct Python handlers. Tests, migrations, `deprecated-guardian_api.py`, docs, comments, and generated files are excluded. Router-level `Depends` and wrapper chains were expanded; the table distinguishes declarations from enabled runtime mounts. A feature-gated row is not a supported-profile or live-ingress claim.

The authority at issue is the Guardian request principal and, separately, the requested resource’s durable owner/participation state. Headers, task IDs, Redis events, and caller-chosen user IDs are evidence or selectors, not authority. For each remote request exactly one of account, operator, or Hosted Room guest may establish a principal. A route-bound service key proves only a non-principal capability. Local single-user authority remains a separate accepted runtime posture.

## Authentication primitive inventory

| Primitive / validator | Material currently accepted | Principal and canonical-account meaning | Remote / local behavior and migration obligation |
|---|---|---|---|
| `auth.issue_session_token` | Explicit subject, TTL, mandatory `purpose` | Issuer only; no inbound principal | Canonical login issues `account_session`; raw-key exchange issues `operator_session`; no default purpose. |
| `auth.verify_session_token_for_purpose` | Signed, unexpired native token with exact requested purpose | Verifier returns subject; account identity still requires canonical store/subject binding | Strict validator exists; account ingress does not consistently use it. |
| `auth.verify_session_token` | Signed, unexpired native token, including historical purpose-less format | No class or account binding by itself | Generic remote paths still accept it without exact purpose; local compatibility cannot define remote authority. |
| `dependencies.verify_api_key` | Preview: approved stored session; other remote: stored session or broad native/JWT Bearer/cookie; local: configured raw `X-API-Key` or Bearer key | Untyped admission result, not a trustworthy account/operator class | Store lookup precedes remote key rejection; remote native/JWT fallback is not exact-purpose; local static-key lane is intentional. |
| `dependencies.require_api_key` | Whatever `verify_api_key` accepts | Wrapper, not independent principal | Used directly, at router level, and through `get_current_user`/other wrappers; replace by route class. |
| `dependencies.get_current_user` and `get_request_user_id/scope` | Generic auth plus Bearer/cookie/store lookup; local single-user/debug identity | Current account-like string/`RequestUserScope`; store lookup lacks purpose check | Private preview maps approved email; generic remote can resolve broad signed subject; local fallback remains. |
| `dependencies.require_operator_auth` | Raw configured Guardian key or exact signed `operator_session` | Operator authority only; no canonical account or `RequestUserScope` | Already gates Continuity; rejects account/guest signed classes; preserve local raw-key operator use. |
| `auth.require_auth` | Raw `X-API-Key`/`X-Guardian-Key`, or broad signed Bearer/`gc_session` | Returns identity descriptor (`api-key`/`session:*`), not canonical account | No remote-purpose rule; `require_user` consumers must migrate to account-purpose/canonical identity. |
| `auth.require_user` | `require_auth` plus optional caller `X-Guardian-Identity` | `AuthenticatedUser` may use caller-provided identity; not canonical account scope | Account exports and federation-context routes currently rely on it; remote raw-key/identity-header path is debt. |
| `auth_dependencies.resolve_session_user_id` / `get_current_user_id` | Bearer/`gc_session` token present in session store | Returns stored account ID with no exact-purpose validation; `get_current_user_id` has local fallback | Purpose check must precede every store resolution; imported `get_current_user_id` in chat/projects has no live route call. |
| `hosted_room_session.decode_principal` + guest route lifecycle checks | `codexify_hosted_room_session`, signed `subject=hosted_room_guest_session`, room/participant/invitation/expiry | Hosted Room guest principal only; never account owner | Routes recheck room, invite, participant and lifecycle; local and remote must keep purpose and scope. |
| `dependencies.require_service_api_key` | Configured raw Guardian key in `X-API-Key` | No principal, account, role, or `RequestUserScope` | Dashboard calls it directly. A dedicated non-principal route dependency is still needed for the five admin operations. |
| `admin.require_admin` and account-observability `_operator_dependencies` | Preview role, legacy `X-Admin-Token`, or bounded local debug; wrapper also calls generic auth/current user | Admin is authorization on canonical account in accepted remote doctrine | Current five-route wrapper is not yet one exact account principal plus dedicated service capability; migration debt, not a doctrine conflict. |

## `require_auth` / `require_user` closure

`require_auth` has no direct exposed route use beyond `require_user`. Exactly six route registrations consume `require_user`: `guardian/routes/api_exports.py::{export_threads,export_account_zip,export_chatgpt_zip}` and `guardian/routes/federation_context.py::{search_context,get_peers,set_peer_trust}` (exact paths in table). Both families are canonical account-user operations, so their primary class is `account_purpose_strict`, not operator or peer-node auth. Their current descriptor plus optional `X-Guardian-Identity` is not a canonical account binding; the later cutover must remove that remote authority path while preserving deliberately local behavior. The separate `guardian/routes/federation.py` node transport is quarantined `internal_nonprincipal`, not this account-bound federation-context family.
