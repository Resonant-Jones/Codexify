# Configuration Operator Inspection Plan

## Purpose and status

This is a documentation-only, architecture-impact plan for a future read-only Configuration Inspector. Its purpose is to show an installation operator which configuration domains exist, which subsystem owns each domain, what value actually won only when that is safely provable, and where a change must be made. It defines inspection requirements, not a runtime resolver, API, database, UI, mutation grant, or release claim.

Evidence posture: documented-contract plus proven-code-path. The 55-family catalog is the inventory baseline; the 30-path authority census is the resolver baseline. Neither is live deployment evidence. The current local-first Beta and HOLD posture remains governed by 00-current-state.md. This plan does not promote its planning labels to protocol tokens.

The proposed Inspector may link to an owning control or operator procedure. It is not a generic configuration database, universal settings editor, environment-variable editor, secrets viewer, replacement for Application Settings, All Settings, Persona Studio or Connections, provider-routing authority, account-administration bypass, runtime health system, or release-support oracle.

## Three distinct product surfaces and trust boundaries

| Surface | Audience and authority | Appropriate content |
|---|---|---|
| Application Settings | Authenticated application user; existing account or client owner | Common editable choices such as appearance and owned identity/memory policy |
| All Settings directory | Application user; directory and links only | Behavioral descriptions, scope and owning control; some entries read-only |
| Operator Configuration Inspector | Installation operator; read-only installation posture | Deployment domains, owner/process scope, safe effective-value evidence, conflict and management location |

The same human may occupy both roles, but an operator session does not thereby gain access to another account's thread, Persona, identity policy, documents, OAuth grants, or cached content. Nodes are browser/desktop clients, Guardian, workers, Redis/Postgres, local Whoosh'd, and optional external providers. The relevant trust boundaries are device to server, account to account, process to process, installation to provider, and secret manager to application. Honest-but-buggy components can report stale values; a compromised node or unauthorized operator can seek secrets or cross-account data. A future projection must enforce role, scope and redaction in code, not in UI wording.

## Effective-value evidence rule

A value may be called **effective** only when the owning resolution path and the winning value are identified for the stated scope, process or request. Record the resolver identity, input-source class, resolution time or generation, relevant override chain, and the process or scope to which the claim applies. An environment declaration, code default, catalog row, Compose pass-through, UI cache, or typed Settings field alone does not meet this rule. A resolver snapshot in one process cannot establish another process's value. If sources conflict, report the conflict and withhold a unified effective value.

| Planning label | Permitted meaning | Example and limit |
|---|---|---|
| Declared | A file, environment source, manifest or default contains a value; the active owner has not been shown to select it. | An env key may be present but shadowed by another source or process. |
| Resolved | The owning resolver can deterministically report the selected non-secret value for its stated scope and generation. | A local desktop bootstrap snapshot can describe that device; it does not describe another device or server. |
| Observed | Runtime evidence shows the active subsystem using the selected value or resulting target. | Guardian route inventory shows mounting; Whoosh'd inventory shows availability; request provenance is needed for the served physical model. Observation does not rewrite configuration. |
| Unavailable | No safe, scoped readback exists, access is prohibited, or resolver conflict prevents a trustworthy claim. | Show ownership, source class and why value is withheld instead of echoing the declaration. |

These are prose labels for future design review, not newly registered runtime tokens or a mandatory lifecycle. Some rows need only presence or ownership, not all four labels. A safe resolved value and a health observation remain separate fields. Configured provider is not available provider; configured model is not served model; mounted route is not an authorized request; OAuth app registration is not a user grant; credential presence is not credential validity; queue name is not worker consumption; selected storage is not healthy storage; graph backend is not write permission; Persona request is not capability grant.

For a secret-bearing field, never render the value, even if its owning resolver knows it. Safe metadata may be configured/not configured, credential owner, source class, or an existing redacted validation state. Never return API keys, passwords, OAuth or session tokens, private keys, attachment grants, webhook secrets, or credential-bearing DSNs. Do not place environment contents in this document.

## Projection matrix conventions

Each row below covers exactly one catalog family. The catalog remains the detailed identifier/source inventory. The compact columns have these meanings:

- **Relevance / visibility:** direct, context, or none; then value, posture, existence, or none. Value means a future non-secret value could be shown **only after** scoped resolver proof. Posture means configured/policy state without raw value. Existence means name and owner only. None means omit from an operator display.
- **Readback and claim:** current safe operator readback is yes, partial, client-only, owner-only, or none; followed by the highest planning label supported by the cited evidence. Partial never licenses an unqualified family-wide effective claim.
- **Change:** current mutation owner/location and effect timing. This plan grants no new mutation.
- **Boundary / companion / gap / presentation:** shadowing, distinct runtime health or availability evidence, privacy restriction, unresolved dependency, and recommended future display. A dash for companion means no separate health surface is needed for this family.

An operator-facing row could safely show a non-secret value only when its particular owner and scope satisfy the effective-value rule above. Most matrix rows therefore say posture or existence even when an installation operator can read a deployment file manually. Health links are adjacent observations, not configuration authority.

### Coverage and inspectability accounting

The three matrices contain 17 U rows, 31 O rows and 7 L rows: **55 distinct catalog IDs**, each exactly once. Visibility postures assign **3 value candidates** (O02, O08 and O15), **28 posture candidates**, **18 existence-only candidates**, and **6 omitted families**. A value candidate is a future conditional presentation, not a claim that all members are currently effective-value readable. Current readback is **yes for one narrow process-scoped observation** (O15 route inventory), **partial for 23 families**, **client-only for 10**, **owner-only for 8**, and **none/unavailable for 13**. Those counts use the family-wide conservative class: a partial or owner-only readback is never generalized to all members or operator access. The selected supported profile, user choice, Compose transport and live model inventory are deliberately different authorities under ADR-074. Connections catalog projection and connector execution/credential ownership remain separate under ADR-071/072. Persona manifest intent, server binding and capability grants remain separate under ADR-082. An Inspector may join their **descriptions** for navigation; it cannot join their authority.

## Recommended future row and detail shape

Each row should bind to a stable catalog family ID and state the narrow scope it describes. A detail view may carry:

| Field | Required meaning or guard |
|---|---|
| Family and purpose | Plain-language behavior, with a link back to the catalog; never treat the document as input |
| Scope and owner | Installation/process/device/account/thread/profile and the owning subsystem; process generation or request identity when a claim is temporal |
| Evidence label | Declared, resolved, observed or unavailable as defined above, with source/proof time and explicit limit |
| Safe value or posture | Non-secret winning value only after owner-scoped proof; otherwise configured/not configured, policy posture or unavailable reason |
| Declared sources and overrides | Source classes and ordered resolution chain, including shadow/conflict warning; redact sensitive paths and endpoints |
| Mutation authority and location | Existing owner/control or operator procedure; the Inspector provides a link, never a write action |
| Effect timing | Immediate, next request, reload, process/worker restart or unknown; keep process-specific timing explicit |
| Privacy and secret rule | Non-secret, redacted-presence-only, user-owned/unavailable, or unknown pending review |
| Adjacent runtime status | Link to health, route inventory, worker receipt, provider inventory or request provenance, visibly separate from configuration |
| Help and source | Governing ADR/contract and bounded evidence reference; show when proof is missing |

A conceptual Local Chat Model row could name the supported profile as policy owner, the Guardian configured logical or exact target as a separate resolved field, and Whoosh'd's advertised route as an observed availability field. It must not collapse those into one “effective physical model”; request provenance is required to identify what served a turn. The row is an illustration of evidence separation, not proposed copy or a claim about the currently running installation.

For a future read-only projection, the operator identity, authorization policy, account-scope filter and redaction must be enforced server-side. A browser-only Inspector can show its own U15/O26 connection snapshot but cannot claim to represent other clients. If the projection aggregates multiple nodes or processes, every observation needs node/process identity, generation and stale/unreachable behavior. On partition or restart, show stale/unavailable with last observation time; do not silently reuse an old value as current. Cache and retry behavior must be bounded and must not turn observations into persistent configuration. Any newly durable inspection receipt would require an explicit owner, retention and access contract.

## Dependency order for a later implementation task

1. **Freeze the first read-only scope.** Select a small set of non-secret installation families such as O02/O15 and the bounded O07/O08 posture. Define operator identity, installation scope, redaction, staleness and the list of omitted user-owned fields. Document current process/route evidence.
2. **Resolve blocking authority questions before unified values.** For O01/O03/O04, O20/O21 and L02, either accept a distinct per-process display or settle precedence through a separate architecture task. Do not invent an Inspector resolver to hide disagreement.
3. **Prove owner-specific readback.** Add only the safe non-secret resolution receipts needed for selected families, with source class, owner, process generation and effect timing. Verify that secret and account data are absent. A health endpoint alone is insufficient for effective configuration.
4. **Accept the operator control-plane contract.** **Requires new ADR** if the Inspector introduces an authenticated aggregation API, durable receipts, new operator access, or cross-process authority semantics. This plan does not create that approval. ADR-071/072/074/082 remain governing boundaries.
5. **Expose a read-only projection.** Implement authenticated, scoped and redacted backend data only after the contract and proof. Preserve owner APIs and existing mutation controls; use unavailable for missing values.
6. **Build the operator UI and adjacent links.** Present family, scope, owner, evidence label, source/conflict, management location and timing. Link health and runtime inventory as separate observations. Do not include edit controls or secrets.
7. **Expand by proven owner.** Add queues, storage, TTS, OAuth and optional paths only after their distinct authority/readback and access gates are verified. Recheck after restart, mixed versions and partial failure; never infer release support from Inspector coverage.

No runtime/API/schema/frontend/Compose/ADR/current-state change is made by this document. Implementation, testing and human acceptance belong to later task packets.
