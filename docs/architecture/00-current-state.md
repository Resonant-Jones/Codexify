## Current supported reality

- The Beta Supported envelope covers local inference, ordinary chat, durable threads/messages/tasks, supported document ingestion and retrieval, account ownership, migrations, and operator diagnostics. Qualification is a separate gate.
- The repository migration graph is a single head, `e723ba9046cd`, across 142 revision files. A head-clean graph is a repository invariant, not a deployment qualification. Earlier live Preview migration evidence applies to its serving source and does not qualify this new source revision. No Preview migration was performed for the custody, credential, connector OAuth or inference-budget changes.
- **The Private Preview's PostgreSQL application database has a verified, dated recovery checkpoint** at `ab71d5ce9604`: the archive was dumped and re-hashed, restored into an isolated disposable container, and its census matched the source. It is preview-lane recovery evidence for the database only, not a release qualification and not a full-environment backup. Four migrations have landed on `main` since it.
- **Account-scoped history recall is implemented on `main` and mounted.** `GET /api/chat/projects/{project_id}/history/search` resolves the account from authenticated authority only, and it is reachable on the supported profile because route posture is per-router and `api_chat` is in that profile's `enabled` posture. The model-facing `op::history.search` tool is advertised only when a request-scoped grant is present. Coverage is code and test level only. **Reader-side per-message origin classification exists; durable same-row custody is pending.** `guardian/core/message_origin_classification.py` classifies each candidate message at read time from its own persisted evidence, and the recall reader excludes imported, unknown and conflicting messages before excerpts reach the model. No schema change, no migration, no backfill. **Accepted architecture is distinct:** the `native_origin_custody` column, migration, trusted creation-only writers, PostgreSQL immutability and custody-aware reader verification are unimplemented -- the identifier appears nowhere in `guardian/` at this tip.
- **Saved Widgets expose more than promotion.** Behind `CODEXIFY_ENABLE_SAVED_WIDGET_ROUTES`, and mounted `enabled` on the supported profile, the API carries `POST /saved-widgets`, `GET /saved-widgets` (account-wide paginated collection listing), `GET /saved-widgets/{id}`, `POST /saved-widgets/{id}/revisions` (explicit new-version append), `GET .../revisions` and `GET .../revisions/{rev}`. Web Library and Scout can list, select and launch an immutable revision client-side. This is still not a qualified widget lifecycle, and the widget UI ships behind the `VITE_GENERATIVE_UI` build flag, which is off by default.
- **The voice lane now enforces account ownership through execution, on a quarantined route.** `guardian/voice/account_access.py` resolves thread authority for both admission and execution, and the voice worker revalidates it before the user message, after transcription, on each token and on cancellation. The `voice` router is `quarantined` in `v1-local-core-web-mcp`, and the Deepgram STT path is a cloud provider the supported profile does not admit. The evidence is code and test level only.
- **The account-import staging path no longer deletes recoverable bytes on an ambiguous commit.** The staging write loop keeps uploaded blobs and lets a retry reuse the same storage names, and the commit is separated from the later refresh and serialization steps. 248 lines of fault-injection tests carry it, including a disposable-PostgreSQL path; no live import receipt exists.

The admin metering route reads the bounded status only when a configuration is present, and it is behind existing account-admin authority on the `admin` router, which the supported profile mounts `enabled`. This is merged code, not a spending control and not qualified execution.
- **The coding-worker lane is merged code, not qualified execution.** Claim persistence is in `guardian/agents/store.py`; the pre-acceptance refusal is deployment-scoped and fenced. None of these merges lifts the gate.
- **The Music Producer surface is merged code behind a quarantining profile.** `music_projects` is not in the default profile's route posture; it is reachable only under `v1-music-producer`, which is not a qualified supported path. ADR-108 is proposed, not accepted. **The host owns the job's attribution**: it records which project a music job belongs to when the handle is minted, in its own `music_jobs` table.

Share *links* are a different surface and remain bearer credentials: `expires_in_days` is optional on creation and no revocation endpoint exists.
